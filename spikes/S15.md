# S15 — Can Open WebUI reach the agent through LiteLLM?

**Status: SPLIT — and the split is the whole finding.** The chain *works*: a real
goose turn came back through LiteLLM on the NAS
(`/a2a/{agent_id}` → `SendMessage` → `TASK_STATE_COMPLETED` → `pong`). The path
an OpenAI-compatible client can actually use — an agent as a **model**
(`a2a/<agent_name>` on `/v1/chat/completions`, and `/v1/responses`) — **does not
work**, and not for a fixable reason: LiteLLM 1.103.0 builds that request itself
in the **A2A 0.3 dialect** while `a2a-lf`/`a2a-server-lf` speak **1.0**. Two
smaller faults surfaced on the way and both are ours: the agent was bound to
loopback while registering a tailnet URL (§6), and nothing told LiteLLM the
bearer the agent requires (§5).

This replaces the assumption every earlier spike left standing: S13 measured
`a2a-rs` against LiteLLM's **routes** and passed; nobody had ever pointed
LiteLLM's **model-facing** A2A client at our agent until now.

## The question

n8n is cancelled (2026-09-17). The caller is **Open WebUI** — an
OpenAI-compatible client that can only POST `/v1/chat/completions` (or
`/v1/responses`) with a model id. So:

1. Can the agent be reached as a *model* through the proxy at all?
2. If not, is there a LiteLLM path that does reach it, and what would it take for
   Open WebUI to use that path?

## Method

On the NAS (`100.82.223.13`, DSM 7.4.1): the agent at **v0.1.25** (goose 1.50.0),
LiteLLM **1.103.0** (`ghcr.io/berriai/litellm:main-latest`, container `litellm`,
network `ai_proxy`, `172.21.0.19`), Open WebUI `main` (container `open-webui`,
already pointed at `http://litellm:4000/v1`).

Three things were used, none of which is a guess:

- the live registry (`GET/PUT /v1/agents`), with the agent registered as
  `nas-goose`;
- a **header-logging listener** on `100.82.223.13:10098`, registered with the
  proxy as a second agent, so the outbound JSON-RPC body, the method name and
  every header are read off the wire rather than inferred;
- `docker exec` + reads of the proxy's own source in the image
  (`/app/.venv/lib/python3.13/site-packages/litellm/`, `a2a-sdk 1.1.0`), and of
  the pinned crates (`~/.cargo/registry/.../a2a-lf-0.3.1`, `a2a-server-lf-0.4.4`).

## 2. Why: the proxy's model paths are A2A **0.3**, hardcoded

The method name is not negotiated and not derived from the card — it is a
literal in the transformation the model paths use:

```python
# litellm/llms/a2a/chat/transformation.py:235
# For A2A protocol, the method is "message/send" for non-streaming
# and "message/stream" for streaming
stream: Final = optional_params.get("stream", False)
method: Final = "message/stream" if stream else "message/send"
```

…with a 0.3-shaped message beside it (`"role": "user"`,
`parts: [{"kind": "text", …}]`, `a2a_message` at `:228`). There is no setting for
this in `litellm_params`, none on the agent row, and no fallback on
`method not found` — measured: the error came straight back.

On our side the names are the 1.0 ones, and they are the only ones the SDK
accepts (S7 already showed the server never reads `A2A-Version`):

```rust
// a2a-lf-0.3.1/src/jsonrpc.rs:138
pub const SEND_MESSAGE: &str = "SendMessage";
pub const SEND_STREAMING_MESSAGE: &str = "SendStreamingMessage";
// is_valid() lists exactly the PascalCase set — `message/send` is not in it
```

The proxy's card handling cannot bridge this, and does not try:
`normalize_agent_card_interfaces` **downgrades** an interface to `0.3` only when
the binding is mis-cased (`"jsonrpc"` vs `"JSONRPC"`) — our card says `JSONRPC`,
so it is left at `1.0` (`a2a_protocol/card_resolver.py:64-87`). That is the
*right* call by that function, and it changes nothing here, because the model
paths never consult the card: `create_a2a_client` (which does resolve the card and
*does* build a 1.0-shaped transport from it,
`a2a_protocol/main.py:744`) is not what these paths call.

So the asymmetry is inside LiteLLM: its **route** is a transparent JSON-RPC
proxy (whatever method the caller sends is what the agent receives — that is why
`SendMessage` works there), while its **model** path is an A2A 0.3 client with a
1.0-registered card in front of it.

## 3. What the route is, and why Open WebUI cannot use it

`_PASCAL_TO_WIRE` (`proxy/agent_endpoints/a2a_endpoints.py:63`) shows the route's
intent: it accepts both spellings from a caller and maps *caller* PascalCase onto
the wire — but for our agent the body is forwarded verbatim, method included
(measured above). Practically: **the route is the only LiteLLM path that can
reach a 1.0 agent today.**

Open WebUI cannot speak to it. Its provider connections are OpenAI-shaped —
`OPENAI_API_BASE_URL=http://litellm:4000/v1` in the container, i.e. every request
lands on `/v1/…`, never on `/a2a/{id}`. And a model id alone is not enough for
the other reason worth writing down: **agents never appear in `GET /v1/models`**
(measured again today: seven models, none `a2a*`), so Open WebUI's dropdown will
not offer one — it has to be added by id.

## 4. Credentials: the proxy sends nothing unless it is told to

Every mark below is from the listener, at `litellm 1.103.0`:

| Lever | Chat / responses | `/a2a/{id}` route |
| --- | --- | --- |
| *(nothing configured)* | no `Authorization` at all | no `Authorization` at all |
| `static_headers` on the agent row | **not sent** | **sent** — this is what made `pong` come back |
| `extra_headers` in the request body | **sent** | n/a |
| `litellm_params.api_key` on the agent row | **not sent** (stored, then ignored) | not sent |
| `x-a2a-{agent}-authorization` header | **not sent** | sent (route only) |

The agent requires its bearer (`constraint #3`: an endpoint that says
"authenticated" and means it), so with none of the above in place the route
answers `401 {"error":"unauthenticated"}` — which is exactly what the first route
call did, and what a naive "it reaches the agent!" observation would have
misread as progress. `static_headers` is the mechanism to use: it is
admin-configured **on the agent row**, so the token never has to travel with a
caller.

## 5. What this means for the plan

The chain is not blocked by our agent or by the network. It is blocked by a
dialect gap in the one path an OpenAI-compatible client can take. Three ways
out, cheapest first:

1. **A bridge in Open WebUI** (a Function/Pipe, ~40 lines of Python) that POSTs
   JSON-RPC `SendMessage` to `http://litellm:4000/a2a/{agent_id}` with a LiteLLM
   virtual key. Works today, keeps the agent and the proxy untouched, keeps the
   caller's credential a *virtual key* (the agent's bearer stays in the row's
   `static_headers`). Cost: a function to own in Open WebUI, and it is not a
   model id in `/v1/models` — but it *is* a model in the dropdown.
2. **A provider override in the proxy**: LiteLLM supports
   `custom_provider_map`, so a handler subclassing the A2A config could send
   `SendMessage` and a role the 1.0 parser accepts. This fixes every
   OpenAI-compatible caller at once and needs nothing in Open WebUI — but it is
   surgery on the proxy's internals, and the response transform (0.3-shaped)
   would have to be checked against our 1.0 task.
3. **A 0.3 face on the agent** (a compat layer mirroring `a2a-sdk`'s
   `compat/v0_3`, which is how the Python SDK carries both dialects). Correct
   long-term — most deployed agents are 0.3 — but it is a protocol
   implementation on our side, against constraint #17, and belongs in
   `a2a-server-lf` (first-party, pinned here) rather than in this repo.

**Decided 2026-09-17: (1) — a bridge in Open WebUI.** It is the only one that
can be true today, it keeps our wire contract intact, and it leaves (2) and (3)
open as the durable answers. The n8n leg was cancelled for the same reason this
works: the caller is one hop, and the hop it needs is JSON-RPC.

## 6. The fault the attempt exposed: the agent was not reachable at all

Before any of the above, every call failed with LiteLLM's own connection error —
`Cannot connect to host 100.82.223.13:10001 … [Connect call refused]`. The agent
was **up** and healthy; the NAS's `~/.config/a2a-goose/env` had

```
export A2A_GOOSE_BIND="127.0.0.1:10001"            # ← loopback
export A2A_GOOSE_PUBLIC_URL="http://100.82.223.13:10001"
```

Measured, and it is the whole fault: the tailnet address is a `/32` on `lo`
(`ip -4 addr`), so a `127.0.0.1` listener does not answer it even from the same
host, and nothing forwards the port.

| Dialled from | `100.82.223.13:10001` | `127.0.0.1:10001` |
| --- | --- | --- |
| the NAS host itself | **connection refused** | 200 |
| this dev box | **connection refused** | – |
| inside the `litellm` container | **connection refused** | – |

The container *can* reach the host's tailnet IP — a listener bound to
`100.82.223.13:10099` accepted a connection from `172.21.0.19` (the container)
almost immediately, which is what S9's re-probe concluded for a peer and what
makes the fix a one-line one. After setting `A2A_GOOSE_BIND="100.82.223.13:10001"`
and letting the boot wrapper restart the agent: `/healthz` 200 from the dev box,
the card fetched fine from inside the container, and the route call above
returned `pong`.

`deploy/env/*.example` carried the same mistake in prose and in value ("Bind
loopback: the only thing that should reach this port is whatever fronts it, and
on this host that is the LiteLLM container dialling `card.url`" — the container
is the dialer, and it cannot dial loopback). Both templates are fixed, and the
agent now **warns** at startup when `bind` is loopback and `publicUrl` is not,
because the only legitimate reason for that shape is a port *fronted* by
something else.

## 7. The bridge, built and measured (same day)

§5(1) was decided and then written: `integrations/openwebui/a2a_bridge.py`, an
Open WebUI **Pipe** function, with its recipe in
[`integrations/openwebui/README.md`](../integrations/openwebui/README.md). It
builds the 1.0 request by hand, authenticates to the **proxy** with a virtual key
(the agent's bearer stays in the row's `static_headers`, §4), and keys
`contextId` on the Open WebUI chat id so a chat is one agent session.

Through Open WebUI's own API — the call the browser makes — on the NAS:

| turn | sent | returned |
| --- | --- | --- |
| 1 | *"Reply with the single word: zeta"* | `zeta` |
| 2 | *"What single word did I ask you to reply with? One word."* — same chat | `zeta` |
| 3 | the same question — different chat | *"…this is the start of our conversation…"* |

Turn 2 is the finding: the answer came from the agent's retained session, not
from re-sent history, which is M3's session reuse measured through two
intermediaries. Turn 3 is the control that makes turn 2 mean anything. And the
route, from inside the Open WebUI container:

```
httpx HTTP Request: POST http://litellm:4000/a2a/0a2d93c6-2b0e-471b-9507-a055b5cfe97d "HTTP/1.1 200 OK"
```

Three things came out of building it, all recorded where they bite:

1. **A completed task carries two `answer` artifacts and one is empty** —
   `{"artifacts": [{"artifactId": "answer", "parts": [{"text": "alpha"}]},
   {"artifactId": "answer"}]}`. The answer is an artifact, and the *second*
   artifact has no `parts` at all. A caller reading `artifacts[0]` survives by
   luck; a caller joining every artifact answers `"alpha\n"`. The bridge collects
   texts and filters empties. Why the agent emits it twice is not explained here
   and is worth its own look at `a2a-server-lf`.
2. **A turn is unary, so nothing streams to the user.** `SendStreamingMessage`
   exists on the agent (`tests/skeleton.rs` pins its SSE frames) and the route
   forwards methods verbatim, but relaying a stream through it is unmeasured, so
   the bridge does not claim it.
3. **The route is not in the model list, and that is what the Pipe is for.**
   Open WebUI synthesises a model entry from an *active* Pipe function; LiteLLM
   will never put an agent in `GET /v1/models` (7 models, none `a2a*`, measured
   again through the §1 method).

The path an OpenAI-compatible client can take is therefore closed by proxying one
hop further out, which is the smallest thing that can be true today.

  <the agent's bearer>"}` (measured necessary: without it the route answers

  where §5's fixture records a `400`. `litellm_params.api_key` is still not an
  alternative: stored and ignored.
- ~~**Open WebUI** — the bridge function of §5(1)~~ — built and measured (§7,
  `integrations/openwebui/`). What remains is the M5 runbook's framings: rotating
  the virtual key, and the note that the agent will never appear in `/v1/models`.
- **Upstream** — a LiteLLM bug report: its A2A *model* paths send 0.3 method
  names to an agent whose registered card advertises 1.0, with no negotiation and
  no fallback (and `static_headers`, which its own route honours, are dropped).
- **`a2a-server-lf`** — if a 0.3 caller ever becomes a requirement, the compat
  layer belongs there, next to the 1.0 types, exactly as `a2a-sdk`'s
  `compat/v0_3` does it in Python.

## Verdict

**SPLIT.** *Can Open WebUI reach the agent through LiteLLM?* **Not as a model** —
LiteLLM's model-facing A2A client speaks 0.3 and the SDK speaks 1.0, and neither
side negotiates. *Can LiteLLM reach it?* **Yes** — the `/a2a/{agent_id}` route
passes the method through and honours `static_headers`, and a real goose turn
(`pong`) came back through it. Between those two facts sits one small function in
Open WebUI, which is the decided fix — written, installed and measured the same
day (§7): an OpenAI-compatible client reaches a 1.0 agent today, through one
extra hop that speaks JSON-RPC. Two faults found on the way are fixed or
recorded rather than guessed at: the agent's loopback bind (§6, fixed on the box
and in both templates) and the missing upstream credential (§4, owed to
`registry.rs`).
