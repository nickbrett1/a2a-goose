# S3 — Exact shapes of the ACP methods

**Plan (§4):** *Drive one real turn through `goose serve` and record every frame.*
**Gates M1's ACP client** (§6.4) and the fixtures the tests replay.

## Method

Harness: `/tmp/acp_sse_probe.py`. Against a real `goose serve` on
`127.0.0.1:3284` it:

1. `POST /acp → initialize` (synchronously; captures the `Acp-Connection-Id`
   response header),
2. opens the **connection-level SSE stream**,
3. `POST /acp → session/new`,
4. opens the **session-level SSE stream** (`Acp-Session-Id: <sid>`),
5. `POST /acp → session/prompt`,
6. records every frame, from both streams, to JSONL.

Every frame is committed, sanitised, as `tests/fixtures/acp-turn.jsonl`.

## Evidence — the transport is POST **plus SSE**, not POST plus WebSocket

This is the spike that corrects the plan. §6.4 assumed *"HTTP POST for requests;
WebSocket read loop for notifications."* The deployed goose says otherwise:

```
# POST initialize -> 200, content-type application/json
# response header: Acp-Connection-Id: <uuid>
# POST session/new  -> 202, body = ''      ; the reply arrives on the CONNECTION SSE stream
# POST session/prompt -> 202, body = ''    ; the reply + updates arrive on the SESSION SSE stream
```

Rules the M1 client must obey, all learned the hard way:

- **Every POST needs `Acp-Connection-Id`.** Without it the server answers
  `Acp-Connection-Id header required`. So `initialize` must be POSTed first and
  its response header held for the lifetime of the connection.
- **Replies are not POST bodies.** A 202 with an empty body is success; the JSON-RPC
  reply must be read from a stream. Reading the body of a `session/new` gets you
  nothing.
- **Two stream scopes.** `session/new`'s reply lands on the *connection*-level SSE
  stream; once a session exists, that session's replies and `session/update`
  notifications land on a *session*-level stream, selected by
  `Acp-Session-Id`. The session stream must be **opened before** the
  session-scoped request is sent, or the reply races past a stream that does not
  exist yet.

Source of truth: `agentclientprotocol/rust-sdk` (`agent-client-protocol-http`
2.1.0, `doc/http-transport.md`) and goose's own
`crates/goose/src/acp/transport/mod.rs`.

## Evidence — the frames

From `tests/fixtures/acp-turn.jsonl` (9 frames, `sess_0001`, one 2-token turn):

| # | Frame | Shape |
| - | ----- | ----- |
| 1 | `session/new` reply | `result.sessionId`, `result.modes{currentModeId, availableModes[]}` |
| 2 | update | `sessionUpdate: "usage_update"`, `{used: 0, size: 200000}` |
| 3 | update | `sessionUpdate: "available_commands_update"`, `availableCommands[]` |
| 4 | update | `sessionUpdate: "session_info_update"`, `_meta.goose.activeRunId` |
| 5 | update | `sessionUpdate: "agent_message_chunk"`, `content{type:"text", text:"ok"}`, `messageId` |
| 6 | update | `session_info_update`, `activeRunId: null` (run finished) |
| 7 | update | `usage_update`, `{used: 33999, size: 200000}` |
| 8 | **prompt reply** | `result.stopReason: "end_turn"`, `result.usage{totalTokens, inputTokens, outputTokens}` |
| 9 | update | `session_info_update`, `_meta.messageCount: 2` |

All notifications are `method: "session/update"` with
`params.sessionId` and `params.update.sessionUpdate` as the discriminator.

The final prompt result, verbatim:

```json
{"jsonrpc": "2.0", "id": 2, "result": {"stopReason": "end_turn", "usage": {"totalTokens": 33999, "inputTokens": 33997, "outputTokens": 2}}}
```

## Verdict

**PASS.** The ACP shapes are pinned, and the fixtures are committed so M1's client
can be tested without a live goose.

## Consequences for the plan

- **§6.4 is wrong about the transport.** It is *HTTP POST for requests + SSE for
  replies and notifications*, not WebSocket. Replace the WebSocket leg
  (`tokio-tungstenite`) with an SSE reader for the ACP hop. (§2.3 keeps
  `tokio-tungstenite` only if the A2A hop needs it — check with S13.)
- **The reply funnel is the hard part of M1**, not the request shape: a single
  connection demultiplexes connection-scope and per-session SSE streams, and
  must correlate JSON-RPC ids back to the awaiting task. This is where the
  timeouts and the reconnect logic will live.
- **`usage_update` gives token counts for free** — cost attribution does not need
  goose's DB for the totals, only for durability.
- The fixture is a **replay contract**: if a goose upgrade changes a frame, the
  test breaks loudly, which is the point.
