# S12 — Does the published binary run on the target host?

**Status: RUN 2026-09-17 on the NAS (DSM 7.4.1, geminilake, x86_64), against the
published release v0.1.25.** The darwin half was seen earlier on mac-studio
(v0.1.16, S11/S14): that host has fetched a published release, unpacked it and
execs it. What follows is the DSM half, run for the first time.

## What to prove

1. The musl static binary for each Linux triple runs on the actual DSM box — for
   the kinds of reasons static + `rusqlite`/bundled + `rustls` (no OpenSSL) were
   chosen in §2.3.
2. `scripts/check-goose.sh` passes **on the host**, with the host's goose. The
   binary refuses to start below the minimum goose (1.50.0) *before* binding a
   port — prove the refusal is the version message, not a bind error.
3. `/healthz` and `/status` answer, and `/status` reports the host's real goose
   path/version.
4. The release assets in the GitHub Release are the ones the launcher fetches and
   the ones that ran — same digest.

## Method

Cold start exactly as `LAUNCHING.md` describes: install the launcher from
`releases/latest/download/fetch-launch.sh`, generate the host's `ENV_FILE`, write
`~/.config/a2a-goose/config.yaml`, then run the launcher and let *it* fetch,
verify, unpack and exec the payload. Everything below is copied from that run.

## Finding 1: the published binary resolves names differently

Registration failed on the first real start, and the error named a host that was
plainly up — `http://nas:4000` — while `curl` from the same shell was answering
`200` from it.

```
{"level":"WARN","fields":{"message":"registration failed; serving locally without a registry entry",
 "attempts":4,"error":"could not reach LiteLLM: error sending request for url (http://nas:4000/v1/agents)"}}
```

Measured, in order:

- `nas` is in **no** DNS zone here. The router (192.168.1.1) answers NXDOMAIN for
  both `nas` and `nas.lan`.
- The only thing that resolves it is DSM's own `/etc/hosts` line — which is
  spelled **`NAS`**, uppercase. glibc matches host names case-insensitively and
  finds it (python's `getaddrinfo("nas", 4000)` → `127.0.0.1`); the musl-static
  payload does not.
- Two temporary `/etc/hosts` lines, one lowercase and one uppercase, isolate
  which half is responsible — a lowercase entry resolves for the payload
  (`registered`), an uppercase one does not (`failed`). So musl *does* read
  `/etc/hosts`; it matches the file's names **exactly**.

The reason an uppercase spelling in the config cannot help either: the `url`
crate lowercases the host before anything resolves it — the error above names
`http://nas:4000` even when the config says `http://NAS:4000`.

**So the value for this host is `http://127.0.0.1:4000`** (the proxy runs in a
container on this same box, publishing `0.0.0.0:4000`), which needs no name
lookup at all. `deploy/env/nas.env.example` said `http://nas:4000`; that is now
corrected there, with this paragraph as the reason. `server.publicUrl` is a
different question and is unchanged: it is what *the container* dials, where
`127.0.0.1` is the container itself (S9), so it stays the tailnet IP literal.

With that one value changed, the payload registered on the first attempt:

```
{"level":"INFO","fields":{"message":"registered with LiteLLM","agent_id":"46ec3f45-0a1d-449c-98fc-db83991ee303","skills":["ask"]}}
```

## 5. A real turn — and finding 2: the header syntax, and the row LiteLLM wrote

Everything above stops at "it answers `/status`". The payload was then asked to
do its actual job on this host — a `SendMessage` turn through the host's goose
1.50.0 and the host's LiteLLM — which failed twice before it worked, each failure
worth more than the success.

**Failure 1 — no provider credential.** `TASK_STATE_FAILED`, `goose refused the
request (-32000): Authentication required`. The transport was fine; goose's
*provider* was not. This box's goose config runs the `litellm` provider against
`http://nas:4000`, and its key normally arrives from `doppler run` in the human's
own invocations — a key the agent-started `goose serve` never sees, because it
inherits `ENV_FILE`'s environment and nothing else. Reproduced outside the agent
with `goose.bin run` under an agent-like environment: `401 Unauthorized … No api
key passed in`. Fixed by adding `LITELLM_API_KEY` to the host's `ENV_FILE`, which
is exactly the job `deploy/README.md` gives that file — and is now a line in both
templates, since `deploy/env/*.env.example` previously carried only the registry
master key.

**Failure 2 — the header syntax, and the reason this is a spike finding.** With
the key in place the provider resolved and the turn failed *differently*:
`-32603 Internal error ("Error getting agent reply: Provider not set")`. The
cause was the file's *identity* line:

```sh
LITELLM_CUSTOM_HEADERS='{"User-Agent":"a2a-goose/nas"}'   # ← every template had this
```

A JSON value makes goose exit `Error invalid HTTP header name` before it can
serve anything. Isolated by pointing `LITELLM_HOST` at a listener on the NAS that
logs request headers and trying five spellings:

| `LITELLM_CUSTOM_HEADERS` | upstream |
|---|---|
| `User-Agent: a2a-goose/nas` | `user-agent: a2a-goose/nas` ✔ |
| `User-Agent:a2a-goose/nas` | `user-agent: a2a-goose/nas` ✔ (space optional) |
| two `x-…: …` lines | both headers ✔ |
| `x-a: 1, x-b: 2` | one header named `x-a` — a comma does not separate ✘ |
| `User-Agent=a2a-goose/nas` | nothing forwarded, no error ✘ |
| `{"User-Agent":"a2a-goose/nas"}` | goose exits `invalid HTTP header name` ✘✘ |

So goose's variable is **`Name: value` lines**, newline-separated for several —
and the spelling that reads "obviously right" is the one that breaks the provider
with a message about a *missing* provider. Corrected in
`deploy/env/{nas,mac-studio}.env.example`, `deploy/README.md`,
`config/config.example.yaml` and `spikes/S2.md`, and the agent now refuses both
bad spellings at startup before it binds a port (`serve::check_child_env`,
unit-tested), so the next host finds out at boot instead of at the first caller's
expense.

## Verdict

**PASS** on both Linux triples' target (the x86_64 musl artifact on DSM; the
darwin artifact on mac-studio was already seen in S11/S14), and PASS on all four
items: the static-PIE binary execs, `check-goose.sh` passes on the host with the
host's goose, the version refusal precedes the bind (with a differential), the
two open endpoints answer and `/status` reports the host's real goose, and the
digest chain from manifest → fetched tarball → running payload holds.

It is now PASS on the thing "the binary runs" only *implies*: the installed
payload **answers a real turn** on this host, through the host's goose and the
host's LiteLLM, and the row LiteLLM wrote for that turn names the host.

Two findings came out of the run, and both are in the repo rather than only here:

- **A published binary's view of names is not the shell's.** The musl resolver
  reads `/etc/hosts` exactly, and DSM spells its own host name uppercase, so
  `http://nas:4000` — the value the templates carried, and which works everywhere
  glibc is — cannot work for this payload on this host. Where a name is optional,
  an address is better.
- **`LITELLM_CUSTOM_HEADERS` is `Name: value` lines, not JSON**, and the JSON
  spelling every template shipped makes goose exit `invalid HTTP header name`,
  which surfaces a long way away as `-32603 … "Provider not set"`. A host
  deployed from those templates could not answer a turn at all.

edit — with the only substitution being a `curl` for n8n. What it does not cover
