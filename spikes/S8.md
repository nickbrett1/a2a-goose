# S8 — Can the agent run as a host process on DSM 7?

**Status: RUN 2026-09-17 on the NAS (DSM 7.4.1, build 90080, geminilake), against
release v0.1.25.** No launchd on DSM, so the boot story is Task Scheduler
(boot-up trigger) plus the keepalive loop in `deploy/dsm/a2a-goose-boot.sh` (§8).
Everything below is measured on the box; the one item not yet observed is a real
reboot, and the section on item 3 says exactly what that would add.

## What to prove

1. Task Scheduler can be pointed at `a2a-goose-boot.sh` with a boot-up trigger,
   running as **goose's user, not root** (hard constraint #9's neighbourhood).
2. The loop actually restarts the launcher after a kill (`kill` the launcher,
   watch the wrapper bring it back within `RESTART_DELAY`).
3. A DSM **package** upgrade or restart does not orphan the wrapper — i.e. the
   process survives what it needs to, and comes back after a reboot.
4. Logs land somewhere retrievable.

## Method

Install the boot-up task, then: fire it, kill the payload, watch, and finally
cold-start the box the way a boot does. The launcher and the payload are the ones
S12 installed; the task body is the one line the wrapper's header documents.

## 1. The boot-up task, as the owner and not as root

`synoschedtask` cannot create a task on DSM 7.4.1 — `--help` offers `--get`,
`--del`, `--run`, `--reset-status`, `--sync` and no `--set`. The GUI's **Triggered
Task** (a *boot-up* trigger) is a different mechanism, `esynoscheduler`, and it has
a CLI. The whole task, created without touching the GUI:

```
$ sudo /usr/syno/sbin/esynoscheduler --create task_name=a2a-goose event=bootup \
    'description=a2a-goose node agent (host process, DSM)' \
    'owner={"1026":"nick"}' enable=true operation_type=script \
    'operation=nohup /volume1/homes/nick/a2a-goose/deploy/dsm/a2a-goose-boot.sh \
       >> /volume1/homes/nick/.local/share/a2a-goose/boot.log 2>&1 &'
```

The CLI's shape is its own: options are `name=value`, `owner` is a JSON object
mapping uid to user name (`{1026:nick}` is silently parsed as an empty object and
rejected), and `--run` fires a task immediately — which is how the loop was
started without rebooting.

The trap, and the reason this item is worth a spike of its own: **the task runs
with root's environment.** Measured, from inside a task owned by uid 1026:

```
$ id
uid=1026(nick) gid=100(users) groups=100(users),101(administrators)
--- env ---
HOME=/root
LOGNAME=root
USER=root
PATH=/usr/local/sbin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
SHELL=/bin/ash
```

So the uid is the owner's and the environment is root's. A wrapper that built its
launcher path from `$HOME` would look for `/root/.local/share/a2a-goose/fetch-launch.sh`
at every boot and find nothing — with the *right* user and the *wrong* home, which
is the failure hard constraint #9 is about ("as root you would mine an empty
recipe directory") wearing a uid-1026 costume.

`deploy/dsm/a2a-goose-boot.sh` was changed for this: it takes the invoking user's
home from `/etc/passwd` (`id -un` reports the owner; only the environment lies),
**exports** it, and only then computes the deploy dir. Exported because the
launcher reads `$HOME/.config/a2a-goose/env` on its way to the exec, and the
payload and the goose below it inherit this environment. Started the way the
scheduler starts it, with `HOME=/root USER=root LOGNAME=root`:

```
$ env HOME=/root USER=root LOGNAME=root nohup ./a2a-goose-boot.sh >> …/boot.log 2>&1 &
$ head -2 boot.log
2026-09-17T14:45:38Z a2a-goose-boot: starting /var/services/homes/nick/.local/share/a2a-goose/fetch-launch.sh
2026-09-17T14:45:47Z fetch-launch: already at 0.1.25
```

and the payload it execs, whose environment is frozen at exec:

```
$ tr '\0' '\n' < /proc/<payload>/environ | grep -E '^(HOME|USER|LOGNAME)='
HOME=/var/services/homes/nick
USER=root
LOGNAME=root
```

The goose child under it reports the same `HOME`, which is what makes it read the
*host's* `~/.config/goose` (recipes and sessions) rather than root's.

A second thing the task body has to respect: **the fire is synchronous.** A task
whose script is `sleep 20` takes 21.3 s, and `esynoscheduler-bootup.service` is
`Type=oneshot` with `TimeoutStartSec=0`. A wrapper that ran its `while :` loop in
the foreground would hold the boot-up event open forever and starve every other
boot-up task on the box — including the one that starts Tailscale. Hence the
`nohup … &` in the task body: fired, the task returns in **2.0 s** and the wrapper
is reparented to init (`ppid 1`), which is also what makes it immune to anything
that happens to the task.

## 2. The loop restarts the launcher

The launcher `exec`s the payload, so the two are one process; killing it is
killing the launcher, which is the same event the wrapper waits on.

```
payload pid before: 9585
$ kill -TERM 9585                      # 14:46:01Z
…                                      # wrapper: "launcher exited with 0 - restarting in 30s"
answered again after 40s               # 14:46:40Z
payload pid after: 20992
```

40 s = `RESTART_DELAY` (30) plus the fetch and the goose readiness gate. The
restarted payload re-registered with LiteLLM on the same terms as the first.

## 3. Coming back

**Fired the boot event itself, rather than a reboot** — this is the code path
systemd runs at boot, and the same command with the same environment and the same
task list:

```
$ sudo /usr/syno/sbin/esynoscheduler --fireEvent event=bootup
…                                     # the box's other boot-up task ran too
real 0m2.616s
healthz after 8s
nick 25019 1    /bin/bash /var/services/homes/nick/a2a-goose/deploy/dsm/a2a-goose-boot.sh
nick 25028 25019 …/current/bin/a2a-goose
nick 26479 25028 /var/services/homes/nick/.local/bin/goose.bin serve --host 127.0.0.1 --port 3284
wrappers running: 1
wrapper ppid: 1
```

and the scheduler's own record of it:

```
"task_name" : "a2a-goose", "trigger_event" : "bootup", "pid" : 25016,
"start_time" : "2026-09-17 10:49:25", "stop_time" : "2026-09-17 10:49:26"
```

One wrapper, owned by init, with the payload and goose under it — from a cold box,
through the real event. **A real reboot has not been run**: it would add two things
only, the boot *order* (the unit is `After=syno-login.target`, so `/volume1` is
mounted) and the state of a machine that has actually restarted. Nothing in the
mechanism is left untested by the fire above, and the loop is itself the backstop
for a volume that mounts late: a launcher that is not there yet is a log line and
a retry in 30 s, not a dead host.

A DSM *package* upgrade was not run either. The measured answer to "can it orphan
the wrapper" is structural: the wrapper's `ppid` is 1, so it is not inside any
package's process tree, and DSM's package restart stops packages, not init.

## 4. Logs, and where they actually land

The wrapper logs twice — stderr, and `logger -t a2a-goose` for the syslog trail —
because the original assumption was `logger` → `/var/log/messages`, which is where
DSM's Log Center reads. **That is wrong on DSM 7.4.1:**

```
$ sudo grep -i a2a-goose /var/log/messages      # nothing, over four restarts
$ sudo journalctl -t a2a-goose -n 3
Sep 17 10:49:25 NAS a2a-goose[25027]: starting /var/services/homes/nick/.local/share/a2a-goose/fetch-launch.sh
Sep 17 10:46:31 NAS a2a-goose[20991]: starting /var/services/homes/nick/.local/share/a2a-goose/fetch-launch.sh
Sep 17 10:46:01 NAS a2a-goose[14654]: launcher exited with 0 - restarting in 30s
```

`logger` from a task lands in the **systemd journal** and never reaches
`/var/log/messages`, which carries DSM's own services (syslog-ng is configured
that way). So the retrievable channels are `journalctl -t a2a-goose` for the
wrapper's own lines, and the task's redirect (`>> …/boot.log 2>&1`) for everything
the launcher and the payload print — which is the one that matters, since the
payload's tracing output goes to stderr and nowhere else. The wrapper's comment
about `/var/log/messages` was corrected to say this.

## The question `deploy/README.md` left open: a SIGKILLed agent

It asked whether a `SIGKILL`ed agent on DSM leaves a goose behind, "because the
next boot would then refuse to start". Measured — it does, and the answer is
better and worse than expected:

```
$ kill -9 31359                                  # the payload
3s later:
nick 1599     1   /var/services/homes/nick/.local/bin/goose.bin serve --host 127.0.0.1 --port 3284
nick 31351    1   /bin/bash …/a2a-goose-boot.sh
listeners: 1                                     # 3284 still held: goose was orphaned
```

```
boot.log:
…/a2a-goose-boot.sh: line 127: 31359 Killed   "$LAUNCHER"
2026-09-17T14:47:42Z a2a-goose-boot: launcher exited with 137 - restarting in 30s
2026-09-17T14:48:12Z a2a-goose-boot: starting …/fetch-launch.sh
{"level":"ERROR","fields":{"message":"refusing to start","error":"http://127.0.0.1:3284 is already in use:
  something is listening there and it answered an ACP `initialize` … Stop it, or set goose.acp.serve to \"external\""}}
2026-09-17T14:48:21Z a2a-goose-boot: launcher exited with 1 - restarting in 30s
```

So: the wrapper does its job (137 → restart), the restarted payload **refuses
loudly and correctly** rather than adopting a goose it did not start, and the
host then sits in a 30-second retry loop with an agent that is genuinely down. It
is not silent — one refusal line per cycle, and `/status` on the port is gone —
but it is **not self-healing**. Removing the orphan by hand heals it on the next
cycle (`recovered after 36s`), and a reboot heals it by construction. That is the
same shape the plan already chose for a goose that will not stay up: loud, and
the init system's problem.

The lesson for the wrapper is the one thing it cannot fix from where it stands:
the payload cannot tell "my goose is an orphan from the process that used to be
me" from "somebody else's goose is there", and it should not try — adopting it is
exactly the mistake the refusal exists to prevent.

## Two things this run could not settle

- **The wrapper itself is not restarted by anything.** launchd restarts a job that
  exits; `esynoscheduler` records the task's exit and moves on. The wrapper is
  thirty lines of bash in a `while :` loop whose only exit is a missing launcher,
  so the exposure is "a reboot fixes it" rather than "it dies quietly", but the
  two hosts differ in kind here and it is written into the wrapper's header.
- **A second wrapper is possible.** The task body is not idempotent: fired while a
  wrapper is already running, the second one's payload refuses on the port and
  retries on the same 30-second cycle. `run_the_same_time` is false, so the
  scheduler will not overlap *its own* runs; nothing stops a stale wrapper from
  before. The visible symptom is a log line every 30 s, not two agents.

## Verdict

**PASS**, on items 1, 2 and 4 outright, and on item 3 as far as a cold start
through the real boot-up event goes: one wrapper, owned by init, bringing up the
payload and goose under it, from nothing. **A real reboot is the one measurement
still outstanding** and is expected to be the same event with `/volume1` mounted
by a boot sequence rather than already.

What this spike changed in the repo: `deploy/dsm/a2a-goose-boot.sh` takes the
user's home from `/etc/passwd` instead of `$HOME` (measured: the task's
environment is root's), and its header now records the task body, the
`esynoscheduler` CLI that creates it, why the body has to detach, and the
journal-not-`/var/log/messages` fact — all of which it previously asserted wrongly
from the reading of the docs rather than from a box.
