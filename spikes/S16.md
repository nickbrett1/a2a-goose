# S16 — Can a session with *any* model find and message the agents?

**Status: PASS — asked, designed, built and measured the same day.** A session
talking to any model can now find the registered agents and hand one of them work:
two MCP tools (`list_agents`, `ask_agent`) served by a small container, registered
in mcphub, and therefore offered by every one of its nine group endpoints — which
is how both a goose session and an Open WebUI model already reach their tools. The
roster is read live on every call, so an agent that comes up is askable at once and
one that is cleared is not offered at all.

This is the other half of [S15](S15.md). S15 made an agent usable *as a model*;
this makes the agents reachable *from a conversation with a different model*.

## The question

Put as the owner put it:

> when chatting with one agent or just another model in openwebui or in a human
> goose session, for that session to be able to find and communicate with my
> agents — so being able to say in a chat with the `core` model, "please follow up
> with the nas agent to complete the task", and it would know that we have an
> exposed nas agent and send it a message. Similar to how it uses MCP tools.

Two surfaces, one requirement: **discovery** (the session must know which agents
exist) and **delivery** (it must be able to send one a message). The follow-on
requirement, stated at the same time, is that a *new* agent must appear by itself
and a cleared one must disappear.

## 1. Why the bridge was not the answer

The S15 bridge is a Pipe: Open WebUI **synthesises a model** from it, which is what
you want when the agent is the thing you are talking to. It gives a model nothing.
`core` had no way to learn that an agent exists, so it could neither name one nor
call one — and no amount of work on the pipe would change that, because the gap is
a missing *tool*, not a missing model.

Three surfaces, three mechanisms, and only the first was done:

| Surface | Mechanism | Before |
| ------- | --------- | ------ |
| Open WebUI, chatting *with the agent* | Pipe / manifold (a model) | ✅ [S15](S15.md) §7 |
| Open WebUI, chatting with **any** model | Tool Server (a tool) | ❌ |
| Human **goose** session | MCP extension (a tool) | ❌ |

## 2. The surface both callers already speak

Before writing anything, three things were checked rather than assumed.

**goose already consumes MCP over streamable HTTP.** The live config on this
machine:

```yaml
extensions:
  mcphub-dev:
    type: streamable_http
    uri: http://nas:8781/mcp/dev
```

So a server added to the hub reaches every session pointed at it, with no
per-machine edit. mcphub (`samanhappy/mcphub`, `nas:8781`) supports
`streamable-http` as an upstream type (`dist/services/mcpService.js`), so the hub
is the place to register it.

**Open WebUI 0.11.3 has native MCP tool servers.** `utils/mcp/client.py` imports
`streamablehttp_client` from the MCP SDK; a connection is `type: 'mcp'`
(`main.py:609`, `middleware.py:1132`); the admin API is
`GET|POST /api/v1/configs/tool_servers` plus `/tool_servers/verify`; and the
container ships `mcp 1.27.2`. Tools from a tool server are visible to **every**
model — that is the `core` case.

**And the wiring was already there.** The finding that made this nearly free:
Open WebUI's existing tool servers *are* mcphub's group endpoints —

```
'mcphub'    -> http://mcphub:3000/mcp/core        'dev'   -> http://mcphub:3000/mcp/dev
'container' -> http://mcphub:3000/mcp/container   'ops'   -> http://mcphub:3000/mcp/ops   …
```

— and the workspace model `core` carries
`meta.toolIds: ["server:mcp:mcphub"]`, i.e. it is bound to the **core group**.
So a server added to the core group is, without any Open WebUI change, a tool that
the `core` model can call. The owner's instinct — "hub routed, everything else is"
— was literally true.

## 3. What was built

`integrations/a2a-mcp/`: one container, `python:3.12-slim` + the MCP SDK, two
tools, and a smoke client. The client logic is the bridge's, deliberately:

- the registry URL is **derived** from the route (`…/a2a` → `…/v1/agents`), because
  two addresses that must agree is the loopback-bind shape again;
- the request is a hand-built A2A **1.0** `SendMessage`/`ROLE_USER` (LiteLLM's
  *route* forwards a method verbatim; its *model* paths hardcode the 0.3 dialect);
- the credential is a **proxy virtual key**; the agent's bearer stays in its
  LiteLLM row;
- the answer is walked, not indexed (`artifacts[*].parts[*].text`), because the
  measured turn carries a second, empty `answer` artifact.

Two decisions that are not obvious in the code:

- **`agent` is matched to how people say it.** `the nas agent` → `nas` →
  `nas-goose`: exact, then a unique substring either way round. An unknown *or
  ambiguous* name is an error that **names the roster**, so a model can correct
  itself in one step instead of guessing twice.
- **The parse code is a copy of the bridge's, not an import.** The bridge must
  remain a single file that installs through Open WebUI's own UI; a shared package
  would break exactly that. Two small functions, with tests on both sides.

**From Open WebUI.** Its MCP client connects to `http://mcphub:3000/mcp/core`

```
    at    | server |    tool     | status  | duration | group_name
----------+--------+-------------+---------+----------+------------
 14:45:10 | a2a    | ask_agent   | success |     2106 | core
 14:45:07 | a2a    | list_agents | success |      128 | core
```

— `list_agents` then `ask_agent`, three seconds apart, in group `core`, from a chat
with the `core` model whose answer was *"The NAS agent replied: **core**"*. That is
the requested behaviour, end to end, through Open WebUI's own API.

**Reachability from the Tailnet**: `GET http://100.82.223.13:8092/a2a-mcp/mcp` →
`406`. Routed by Traefik and answered by the server, which is POST-only by design
(the same `406` a bare `GET` gets directly).

## 5. What Open WebUI's own API does, and what I could not close

Three request shapes, measured, and they are not interchangeable — this is worth
knowing before anyone automates a chat:

1. **No `tool_ids`, no `chat_id`** (the plain OpenAI-compatible call): tool
   resolution is skipped entirely unless tools are named, and the runs disagreed
   with each other — one returned the agent's answer, others had the model answer
   as if it had no tools, and one had the model **render the tool call as JSON
   text** (`{"tool_calls": [{"name": "a2a-ask_agent", …}]}`) in its content. The
   plumbing is not what varies here; the model's willingness to emit a native
   tool call is.
2. **With `tool_ids`**: the model emits a real tool call (`mcphub_a2a-list_agents`)
   and Open WebUI executes it — mcphub logs the call.
3. **With `chat_id`**: Open WebUI switches to its background-task shape,
   `{"status": true, "task_ids": [...], "chat_id": ...}`, and the conversation is
   delivered over its socket rather than the HTTP response. A probe that polls the
   chat over REST sees an empty chat, because no socket client is attached — this
   is also why my first attempts to "read the answer back" looked like failures.

What this *does* mean: the in-browser UI is the path these tools are built for, and
it behaves like (2)+(3), not like (1). What it does **not** mean: that a given model
will reliably choose the tool. `deepseek-v4-flash` called it on some runs and
narrated the call as text on another. That is a model property, not a wiring one,
and it is the one piece of the user-facing experience this spike leaves to the
first real chat.

## 6. What this owes, and what it inherits

- ~~**The M4 hole, now with three dependants.** This server, the bridge and the
  Open WebUI dropdown all reach the agent through LiteLLM's route, and all three
  depend on the agent row's `static_headers` carrying the bearer.~~ — **closed**
  (`registry.rs`): registration sends the bearer in the row itself, so the
  hand-made admin `PUT` on the NAS is no longer the only thing holding the three
  surfaces up. The hole is what S16 exposed; the fix is S15 §"what is owed"'s
  first bullet, done — and **measured on the box** in `v0.1.35`: the NAS payload
  was `SIGTERM`ed, the launcher fetched the new release, and the row came back
  carrying the credential with no admin `PUT` in the sequence (S15, the same
  bullet, for the timestamps and the two things it does *not* prove).
- **A tool call blocks for the whole turn.** 300 s here; mcphub's and Open WebUI's
  own tool-call timeouts were not measured, and a multi-minute turn through a hub
  is untested.
- **Unary.** `SendStreamingMessage` exists and the route would forward it; relaying
  a stream is unmeasured.
- **A `.env` in the working directory is read by the MCP SDK's settings.** Not a
  hazard in the image, but it is why the tests mount into `/app` instead of running
  from the deployment directory. Found the hard way: the first test run died with
  `PermissionError: '.env'` because the container's unprivileged user could not
  read the 0600 file it found in its cwd.

## Verdict

**PASS.** The question was "can a session with any model find and message the
agents, like it uses MCP tools", and the answer is yes, on every surface: a goose
session through its hub group, an Open WebUI model through the tool server it was
already bound to, and any other MCP client through the proxy URL. The agents are
discovered live — the follow-on requirement — because the roster is read from
`GET /v1/agents` on every call rather than cached in a list.
