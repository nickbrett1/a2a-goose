# S10 — Recipe mining: where do recipes live, and is the shape stable?

**Plan (§4):** *Find the recipes the host goose already has, and confirm the plan's
`id ← recipe name` mapping.* **Gates §6.3** (the skill catalogue that projects
recipes as skills).

## Method

Enumerate the recipe locations the hosts already use, list what is there, then
dump the top-level keys of every recipe found.

```
ls ~/.config/goose/recipes/*.yaml
python3 -c "import yaml,sys; [print(sorted(yaml.safe_load(open(f)).keys())) for f in sys.argv[1:]]" ~/.config/goose/recipes/*.yaml
```

## Evidence — where recipes live

| Location | Source | Notes |
| -------- | ------ | ----- |
| `~/.config/goose/recipes/*.yaml` | goose, user recipes | one file per recipe; the natural skill source |
| `GOOSE_RECIPE_PATH` dirs | goose, documented env var | additional recipe directories, searched in addition to the above |
| (bundled/internal) | goose binary | not enumerable as files; out of scope for mining |

## Evidence — the shape, and the correction

Top-level keys seen across the host's recipes:

```
["version", "title", "description", "parameters", "prompt", "instructions"]
```
and, for `scaffold-project.yaml` additionally:
```
["version", "title", "description", "parameters", "prompt", "instructions", "extensions"]
```

**There is no `name` field.** The recipe's identity in the file is its
`title` (human) and its filename (machine). The plan's §6.3 mapping *"skill `id`
← recipe `name`"* therefore refers to a field that does not exist.

## Verdict

**PASS, with one correction to §6.1/§6.3.** Recipe mining is viable at 1.50.0 —
recipes are plain files in a predictable directory, stable in shape, and already
present on the hosts. But the id must be derived, not read:

- **`id` ← the filename stem** (`scaffold-project.yaml` → `scaffold-project`).
  Stable, filesystem-unique within a directory, and what a user would type. On a
  collision across `GOOSE_RECIPE_PATH` dirs, first-wins with a logged warning.
- **`name` ← `title`** (falling back to the id), for display only.
- **`description` ← `description`**, `prompt`/`instructions` → the skill's
  instruction text.

## Consequences for the plan

- §6.1/§6.3 — replace "id ← recipe name" with "id ← filename stem; name ← title".
- `parameters` is a first-class recipe field: skills projected from recipes that
  take parameters are **not** callable from A2A without a way to supply them.
  M1's skill projection should either (a) skip parameterised recipes from the
  default catalogue, or (b) expose them with the parameters as declared skill
  inputs. Decide in M1; do not silently expose them.
- `extensions` in a recipe is a **security-relevant** field: a recipe can pull in
  extensions. Mining is not a sandbox, so §6.3's `enabled`/`overrides` lists
  (allow/deny by id) are load-bearing, not cosmetic.
- `GOOSE_RECIPE_PATH` is the documented way to add directories — the agent adds
  none by default and only reads what it is told to.
