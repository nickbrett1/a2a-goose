## The two halves of the question

S9 asks two things that turned out to be separable:

1. **Addressing.** Can the LiteLLM container open a socket to the agent at the
   URL we register? (This is what gates §6.2's `card.url` and the config
   example's "`publicUrl` must not be loopback" warning.)
2. **The card fetch.** Having reached it, does LiteLLM read the card and record
   our skills — or is `skills: [chat]` in `GET /v1/agents` LiteLLM's own
   synthesis?

Half one is a yes. Half two is a hard no, and the mechanism is not "the fetch
failed" — it is "there is no fetch".

## Method

On the NAS (DSM 7, `geminilake`, `100.82.223.13`), via a shell on the host and
`sudo -n docker exec litellm`. LiteLLM is `ghcr.io/berriai/litellm:main-latest`
(image built 2026-09-16, **litellm 1.103.0**), network `ai_proxy`. The image has
no `curl`/`getent`, so container-side probes are raw sockets from its own
`python3`. The agent on mac-studio is a host process (`com.nick.a2a-goose`,
launcher v0.1.20, goose 1.50.1).

## Half 2 — The card fetch: FAIL, because LiteLLM 1.103.0 has no fetch on the registration path

### What we measured, repeatedly

`GET /v1/agents` returns exactly one entry, `skills: [chat]`, with the URL now
reachable:

```
[{'id': '7c93a422-4163-409f-96d1-39a4771b9d71',
  'name': 'mac-studio-goose',
  'url': 'http://192.168.1.33:10001',
  'skills': ['chat']}]
```

The agent assembled `skills: ["ask"]` and registered cleanly **five** times —
00:32, 10:29, 11:00:17, 11:00:54, and a fresh `launchctl kickstart -k` at
11:17:07 — each ending in a clean `deregistered from LiteLLM` on the way out and
a new `registered with LiteLLM … skills: ["chat"]`. Every registration returned
LiteLLM's synthesised card, including the ones with a reachable LAN URL:

```
{"message":"card assembled","name":"mac-studio-goose","skills":"[\"ask\"]", ...}
{"message":"registered with LiteLLM","agent_id":"7c93a422-…","skills":"[\"chat\"]"}
```

Re-registration is not the remedy. It cannot be: there is nothing for it to
re-fetch.

### Why — the code path, read in the container

`POST /v1/agents` (`litellm/proxy/agent_endpoints/endpoints.py`, `create_agent`)
does **not** make any request to `card.url`. It takes the posted
`agent_card_params`, refuses to synthesise for a plain LLM agent, and otherwise
passes the caller's card straight through `merge_agent_card`:

```python
upstream_card: Final = request.get("agent_card_params")   # ← the POST body, not a fetch
...
merged_card = _build_merged_agent_card(upstream_card, agent_id=…, http_request=…)
```

`merge_agent_card` (`litellm/proxy/a2a/agent_card.py`) takes the upstream card
**as given** and only fills defaults — including `_DEFAULT_SKILLS`, which is
literally the `chat` skill:

```python
_DEFAULT_SKILLS = [{"id":"chat","name":"Chat",
                    "description":"Conversational interaction with the agent.","tags":["chat"]}]
...
if not base.get("skills"):
    base["skills"] = deepcopy(_DEFAULT_SKILLS)
```

We register exactly three fields —
`agent_card_params {name, url, protocolVersion}` (deliberately no skills,
`src/registry.rs`) — so `base.get("skills")` is empty and LiteLLM stamps in
`chat`. That is the whole of it.

The **only** card-fetching code in the image is a *manual, admin-driven*
discovery endpoint:

- `POST /v1/a2a/discover` (`litellm/proxy/a2a/endpoints.py`) calls
  `fetch_well_known_card` (`litellm/proxy/a2a/discovery.py`), which tries
  `/.well-known/agent-card.json`, `/.well-known/agent.json`, `/agent.json`.
- Its own module docstring: *"used by the LiteLLM UI when an admin registers a
  new A2A agent … the raw card so the UI can render the agent's skills … for the
  admin to pick which ones to expose."* The merge then happens when the **admin**
  saves via `POST /v1/agents`.

So in the intended flow the human, not the proxy, supplies the skills. A node
agent that self-registers programmatically has no path that ever reads its card.

And even that manual path is closed to us on this host — here is the
discovery call:

```
$ curl -s -X POST http://127.0.0.1:4000/v1/a2a/discover \
    -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H 'Content-Type: application/json' \
    -d '{"url":"http://192.168.1.33:10001"}'
{"detail":"Could not fetch agent card from http://192.168.1.33:10001
 (mode=well_known_fallback). Last error: …/agent.json: URL targets a blocked
 address (192.168.1.33). If this is a legitimate internal service, add the host
 to `user_url_allowed_hosts` in general_settings."}   (HTTP 400)
```

`fetch_well_known_card` routes through `async_safe_get`, which enforces the SSRF
blocklist and refuses private/loopback targets — so the one mechanism LiteLLM
has for reading a card answers **400** for our LAN address. (This is also why the
earlier `GET /.well-known/agent-card.json → 404` lines in the container log are
*incoming* probes, not an upstream fetch: LiteLLM has no root route for that
path.)

The other place a `url` is dialled — `_check_agent_url_health`, used only to
populate a health flag in the `GET /v1/agents` listing — does a plain `GET` on
the URL, reads no card, and writes nothing back.

### Verdict on half 2

**FAIL, and not as S5 framed it.** S5 said LiteLLM "fills in the real card later
(or not at all)". There is no later. `[chat]` does not mean "the fetch has not
happened yet"; it means **LiteLLM never asks**. On 1.103.0 a self-registered
agent's skills are invisible to the proxy unless the *caller of
`POST /v1/agents` supplies them*. §12.6 applies: this is a decision, not a quiet
workaround.

## Task 5 — the addressing decision, recorded

- ~~**`card.url` is `http://192.168.1.33:10001`** — the LAN literal.~~
  **SUPERSEDED same day:** `card.url` is now `http://100.77.144.14:10001`, the
  tailnet IP literal (see re-probe section) — it removes the DHCP-lease
  dependency entirely, which is what the next bullet was asking for.
- **`192.168.1.33` is a DHCP lease, 24 h** (`ipconfig getpacket en0`:
  `yiaddr = 192.168.1.33`, `server_identifier = 192.168.1.1`,
  `lease_time = 0x15180` = 86400 s). A card URL pinned to a lease is a latent
  failure: it wants a **reservation** (so the literal is stable) or a **name**.
  mac-studio's names are `mac-studio` (LocalHostName/ComputerName) and
  `mac-studio.local` (mDNS). A reservation on the router (192.168.1.1) is the
  low-risk fix; a name only helps if the container can resolve it — its resolver
  is Docker's embedded DNS, so `.local` is not guaranteed and would need to be
  tested.
- ~~**The tailnet is off the table** for NAS→peer dialling (userspace mode, no
  outbound route).~~ **SUPERSEDED same day:** NAS→peer dialling works over
  `tailscale0`; the tailnet IP is the address in use (see re-probe section).
- **`http://127.0.0.1:10001/healthz` is `000`** on mac-studio — the bind moved to
  the LAN address, so loopback no longer serves; checks written against loopback
  must use the LAN address. `goose.acp.url` stays `127.0.0.1:3285` (loopback is
  correct there — goose is the agent's child).

## Consequences and the escalation

For the plan and the registry work:

1. ~~**§6.2's `card.url` is settled**: it is a host-reachable **LAN literal**, and
   on this box "reachable" means "not loopback, not `100.x`, not `*.ts.net`".~~
   **SUPERSEDED same day:** it is a host-reachable **tailnet IP literal**
   (`100.77.144.14`), not loopback and not a `*.ts.net` name; `*.ts.net` still
   fails *DNS* inside the container. See the re-probe section.
2. **S5's card note is corrected**: the real card is not "filled in later" — it
   is never fetched. Any test that asserts on `skills` must expect `[chat]` from
   *any* self-registration on this LiteLLM version, reachable URL or not.
3. **The decision (§12.6)** — to get our skills into the registry, one of these
   must be chosen; none can be taken quietly, and the last two are the ones the
   memo's "do not" list was protecting against:
   - **A. Declare the assembled card in the registration payload.** `registry.rs`
     already assembles the card from the host's own recipes (`card.rs`); send
     those `skills` in `agent_card_params` instead of only `{name,url,version}`.
     The card still comes from the host's recipes — the objection in the memo
     ("that forks the card away from the host's recipes") is about *LiteLLM*
     synthesising, which this avoids — but it does move card ownership into the
     agent's POST.
   - **B. A reconciler that discovers then PUTs.** Call `POST /v1/a2a/discover`
     to fetch the card, then `PUT /v1/agents/{id}` with the merged card. This
     keeps LiteLLM as the card source, but always needs the SSRF allow-list
     below and a new moving part (the sweeper's neighbour).
   - **C. Patch LiteLLM** to fetch the card server-side. Out of our repo; a fork.
   All three need, for the LAN address to be usable at all from a
   LiteLLM-issued request,
   **`user_url_allowed_hosts` to include `192.168.1.33`** (or the host/name)
   in `general_settings` — without it even B returns 400, as measured above.
4. **S13's follow-ups** — "which card path the proxy fetches, and whether it
   forwards `metadata`/SSE" — are now answerable for the card path: it fetches
   *none* on the registration route, and the only fetcher is the manual
   discovery endpoint (SSRF-gated). SSE forwarding remains open.

# Amendment 2026-09-17 (later the same day) — the NAS's tailnet does outbound now

The Tailscale install on the NAS was fixed after the measurements above: it can
now make **outbound** tailnet connections. That reverses the finding that made
this spike answer "LAN literal, and the tailnet is never an option", so the
addressing half was **reopened — in a good way**:

- **Everything above is the *pre-fix* measurement.** It is kept intact as the
  record, but the two tailnet rows (`mac-studio.tail86fd19.ts.net:10001`,
  `100.77.144.14:10001`) no longer describe the NAS. Re-run below.
- **A tailnet address is the better answer if it holds.** `192.168.1.33` is a
  24 h DHCP lease, so the LAN literal is a latent failure; a `100.x` address is
  static and survives a lease change. The card-ownership decision (option A,
  above) makes this a **one-line change on our side** — the registered `url` is
  ours to set in the registration payload, so no LiteLLM change and no
  `user_url_allowed_hosts` entry is needed, exactly as A needs none.
- **DNS, not the route, is the thing to actually test.** The container resolves
  through Docker's embedded resolver (`127.0.0.11`), which forwards to the
  *host's* resolvers; the host gaining an outbound tailnet route does not by
  itself make MagicDNS names resolve inside the container. If
  `mac-studio.tail86fd19.ts.net:10001` still fails DNS but
  `100.77.144.14:10001` connects, register the **IP literal** — that is the
  outcome that fixes the DHCP problem.
- **Nothing else in this spike changes.** The card half (LiteLLM 1.103.0 never
  fetches, `skills: [chat]`, the SSRF block on private addresses) is unaffected
  by the transport, and option A — register the assembled card ourselves — stays
  the decision and stays implemented (`e7bffb9`).
- `memos/X5yyHDyC4TSa6G2aRY52FV` ("PARKED: NAS tailscale outbound is dead") and
  the "tailnet is off the table" note in `memos/f4nMA9MBw5f5V9owP8piRs` are both

### `card.url` moved to the tailnet literal — and the card came with it

mac-studio's `~/.config/a2a-goose/env`:

```

export A2A_GOOSE_PUBLIC_URL="http://100.77.144.14:10001"
```

2026-09-17, [S15](S15.md) §6): the NAS's env kept

registered an address nothing listened on — `/healthz` 200 on the box, connection

### What this changes, and what is still open

- **`card.url` is settled as the tailnet IP literal.** Static, host-reachable
  from the container, and no longer coupled to a DHCP lease.
- **The DHCP reservation (task 5) is now optional.** It is tidy but no longer
