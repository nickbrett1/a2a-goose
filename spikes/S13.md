# S13 — Is `a2a-rs` wire-compatible with LiteLLM's A2A routes?

**Status: NOT RUN.** Gates M1: it is the spike that proves the two halves of the
system can talk before we build the middle. Deferred only because it needs an
a2a-rs server to exist (M1) — the *first* thing M1 must do is re-run this.

## The question

Do the pinned crates

```
a2a-lf        0.3.1
a2a-server-lf 0.4.4
a2a-client-lf 0.2.5
```

speak a wire format LiteLLM's A2A routes actually accept — and do LiteLLM's
replies parse back? A version-pin that compiles proves nothing about the wire.

This is why the pins are the **contract**, not a preference: `Cargo.lock` is
committed and every CI build is `--locked` (§3), and Dependabot is told to ignore
`a2a-lf`, `a2a-server-lf` and `a2a-client-lf`. An unreviewed bump here is a
protocol change, so it must not auto-merge.

## Method, once M1's server exists

1. **Loopback.** `a2acli` → our own server, `message/send` and
   `message/stream`, card at `/.well-known/agent-card.json`. Proves the SDK is
   self-consistent (and gives the [S7](S7.md) harness).
2. **Through LiteLLM.** Register the node agent (`POST /v1/agents`) and call it at
   LiteLLM's **synthesised** route:
   `POST http://nas:4000/a2a/{agent_id}`. This is the route the synthesised card
   advertises ([S5](S5.md)), and it is the one a real caller uses.
3. **Watch the seams.** Specifically: does LiteLLM forward the JSONRPC body
   verbatim, or rewrite it? Does it pass `A2A-Version`/`a2a-version` through (see
   [S7](S7.md))? Does a streaming call survive the hop, or arrive as one buffered
   response? Does LiteLLM's own default card (`skills: [{id: "chat"}]`) shadow the
   card our server serves?

## Why it must be first in M1

Everything downstream — the card, the executor, the session lifecycle — is only
worth building if the framing is right. If a2a-rs and LiteLLM disagree about the
wire, that is a **§12.6 escalation** (it would change the SDK choice or the
integration topology) and we want to hit it on day one of M1, not after the
executor is written.

## Pre-conditions

- M1's server serves a card and answers `message/send`.
- A registered agent (registration is best-effort and may pin a default card —
  see [S5](S5.md) — so assert on **skills**, and re-register after the card is
  stable).
