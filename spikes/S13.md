# S13 — Is `a2a-rs` wire-compatible with LiteLLM's A2A routes?

**Status: PASS, with three follow-ups.** Gates M1: it is the spike that proves the
two halves of the system can talk before we build the middle. It was deferred
because it needs an a2a-rs server to exist, so M1 built one first and then ran
this.

The framing is compatible. The **card** is not, in two independent ways — and the
proxy's card-fetch path could not be settled from here, because its container
cannot route to the agent at any address we tried. The card gaps are absorbable
on our side without changing the SDK choice or the topology, so this is **not** a
§12.6 escalation. Details below, and the follow-ups are named at the end.

## The question

Do the pinned crates

```
a2a-lf        0.3.1
a2a-server-lf 0.4.4
a2a-client-lf 0.2.5
```

speak a wire format LiteLLM's A2A routes actually accept — and do LiteLLM's
replies parse back? A version-pin that compiles proves nothing about the wire.

This is why the pins are the **contract**, not a preference: `Cargo.lock` is
committed and every CI build is `--locked` (§3), and Dependabot is told to ignore
`a2a-lf`, `a2a-server-lf` and `a2a-client-lf`. An unreviewed bump here is a
protocol change, so it must not auto-merge.

## Method

The plan said `a2acli`. **There is no `a2acli`** — not on `PATH`, not in
`cargo --list`, not shipped by any of the three pinned crates. Substituted with
the two things that actually exercise the wire and that M1 can keep:

1. **Loopback** — raw JSON-RPC over `curl` against our own server, plus the
   pinned **SDK client** (`a2a-client-lf` 0.2.5) driving the same calls. The raw
   calls pin the bytes; the SDK client proves the client half of the pair agrees
   with the server half. Both are committed as tests, so this is re-run by CI
   rather than remembered: `tests/skeleton.rs` (SDK + raw wire) and
   `tests/litellm_card.rs` (LiteLLM's card against our card model).
2. **Through LiteLLM** — register the agent (`POST /v1/agents`) and call it at
   LiteLLM's route `POST http://nas:4000/a2a/{agent_id}`, the route the
   synthesised card advertises ([S5](S5.md)) and the one a real caller uses.
3. **Watch the seams** — body forwarding, `A2A-Version` handling, streaming
   across the hop, and whether LiteLLM's default card shadows the one we serve.

## Half 1 — loopback: PASS

Our server, booted on `127.0.0.1:10099`, card and skill catalogue assembled from
the real host config.

```console
$ curl -s http://127.0.0.1:10099/.well-known/agent-card.json
{"name":"mac-studio-goose","description":"goose on the Mac Studio, via A2A",
 "version":"0.1.0",
 "supportedInterfaces":[{"url":"http://mac-studio.tail86fd19.ts.net:10099",
                         "protocolBinding":"JSONRPC","protocolVersion":"1.0"}],
 "capabilities":{"streaming":true,"pushNotifications":false},
 "defaultInputModes":["text/plain"],"defaultOutputModes":["text/plain"],
 "skills":[{"id":"ask","name":"Ask","tags":["chat"],…},
           {"id":"code-review","name":"Code review","tags":["review","quality"],…}]}
```

`ask` is the built-in and `code-review` came from `skills.d/`, so the served card
proves the whole catalogue path, not just a hardcoded one.

| Call | Result |
| ---- | ------ |
| `GET /.well-known/agent-card.json` | **200**, a2a-lf 1.0 card (`protocolVersion: "1.0"`) |
| `POST /` with no `Authorization` | **401** |
| `POST /` `SendMessage`, `metadata.skillId: "code-review"` | `TASK_STATE_COMPLETED`, `ROLE_AGENT`, echo `stub: skill=code-review dispatch=instruction cwd=/tmp message=hello` |
| `POST /` `SendMessage`, `metadata.skillId: "nope"` | **-32602** `unknown skillId "nope"; this agent offers: ask, code-review` |
| `POST /` method `"message/send"` | **-32601** `method not found: message/send` |
| `POST /` `SendStreamingMessage` | one SSE frame: `id: 1` + `data: {…"state":"TASK_STATE_COMPLETED"…}` |

Evidence, verbatim:

```json
{"jsonrpc":"2.0","id":1,"result":{"task":{"contextId":"01a0ab1a-1cbe-73df-a474-f6430ff8e5e0","id":"01a0ab1a-1cbe-73df-a474-f642bec352f2","status":{"message":{"messageId":"01a0ab1a-1cbe-73df-a474-f64443e24616","parts":[{"text":"stub: skill=code-review dispatch=instruction cwd=/tmp message=hello"}],"role":"ROLE_AGENT"},"state":"TASK_STATE_COMPLETED","timestamp":"2026-09-16T16:43:30.366436891+00:00"}}}}

{"jsonrpc":"2.0","id":2,"error":{"code":-32602,"message":"unknown skillId \"nope\"; this agent offers: ask, code-review","data":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo","domain":"a2a-protocol.org","metadata":{"timestamp":"2026-09-16T16:43:30.375115479+00:00"},"reason":"INVALID_PARAMS"}]}}

{"jsonrpc":"2.0","id":3,"error":{"code":-32601,"message":"method not found: message/send","data":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo","domain":"a2a-protocol.org","metadata":{"timestamp":"2026-09-16T16:43:26.318768329+00:00"},"reason":"METHOD_NOT_FOUND"}]}}
```

```
id: 1
data: {"jsonrpc":"2.0","id":4,"result":{"task":{"contextId":"01a0ab1a-0cf7-76d1-b51d-9d4dd8829a13","id":"01a0ab1a-0cf7-76d1-b51d-9d4cd79b16e9","status":{"message":{"messageId":"01a0ab1a-0cf7-76d1-b51d-9d4eabb0221d","parts":[{"text":"stub: skill=ask dispatch=ask cwd=<goose default> message=stream me"}],"role":"ROLE_AGENT"},"state":"TASK_STATE_COMPLETED","timestamp":"2026-09-16T16:43:26.327503876+00:00"}}}}
```

Three things this settles beyond "it works":

- **The method names are ProtoJSON camel case.** `SendMessage`, not
  `message/send`. The slash names are `METHOD_NOT_FOUND` (-32601), not a parse
  error — a caller using the older vocabulary gets a clean, diagnosable refusal.
- **The error envelope carries a typed detail.** Every error appends a
  `google.rpc.ErrorInfo` with `domain: "a2a-protocol.org"` and a `reason` that
  mirrors the code constant. That is a stable thing to assert on, and
  `tests/skeleton.rs` does.
- **Streaming is SSE with `data:` frames**, not one buffered body — so the M1
  transport really is POST + SSE ([S3](S3.md)) end to end, not just on the ACP
  leg.

The SDK client (`a2a-client-lf` 0.2.5) drives all of the above in
`tests/skeleton.rs`, negotiating from the served card. It has one sharp edge
worth recording: **`create_from_card` dials the `url` in the card**, so a test
that fetches the card from `127.0.0.1:0` still calls the advertised public URL
and fails at the socket. The test fixture rewrites
`supportedInterfaces[0].url` to the bound address before dialling. Nothing is
wrong with the SDK — but it means the *card's url is the address*, and getting it
wrong is a connect error, not a protocol error.

## Half 2 — through LiteLLM: registration PASS, card synthesised

Registration works and the agent is callable *as a route*. What does **not**
work is the assumption that LiteLLM reads the card we serve.

```console
$ curl -X POST http://nas:4000/v1/agents -H "authorization: Bearer $KEY" -d '{
    "agent_name": "s13-live-registration",
    "agent_card_params": {"name": "mac-studio-goose",
                          "url": "http://mac-studio.tail86fd19.ts.net:10099",
                          "protocolVersion": "1.0"}}'
{"agent_id":"a496c7fa-7439-455c-b46d-f304102bab91", "agent_name":"s13-live-registration", …}

$ # our own log, same moment
"message":"registered with LiteLLM","agent_id":"a496c7fa-…","skills":"[\"chat\"]"
```

`skills: ["chat"]` is the tell. LiteLLM's own default skill, not `ask` and
`code-review`. `GET /a2a/{agent_id}/.well-known/agent-card.json` returns
**LiteLLM's synthesised card**:

```json
{"url":"http://nas:4000/a2a/00000000-0000-0000-0000-000000000000",
 "name":"s13-probe-agent",
 "skills":[{"id":"chat","name":"Chat","tags":["chat"],
            "description":"Conversational interaction with the agent."}],
 "version":"1.0.0",
 "provider":{"url":"http://nas:4000","organization":"LiteLLM Proxy"},
 "security":[{"LiteLLMKey":[]}],
 "capabilities":{},
 "protocolVersion":"1.0",
 "securitySchemes":{"LiteLLMKey":{"type":"http","scheme":"bearer",
                                  "description":"LiteLLM virtual key"}},
 "defaultInputModes":["text"],"defaultOutputModes":["text"],
 "supportedInterfaces":[{"url":"http://nas:4000/a2a/00000000-0000-0000-0000-000000000000",
                         "protocolBinding":"JSONRPC","protocolVersion":"1.0"}]}
```

(Committed as `tests/fixtures/litellm-agent-card.json`, agent id zeroed and probe
name neutralised.)

So: **the proxy rewrites the address, keeps its own provider and security
scheme, and substitutes its own skill list.** `GET /v1/agents/{id}` shows our
`agent_card_params` stored verbatim, so nothing is lost — but what a *caller*
reads at the A2A route is LiteLLM's card. **Through LiteLLM, our skills are
invisible to discovery.** Skill routing can still work — `metadata` travels in
the JSON-RPC body — but nothing about §6.1's card actually reaches a
proxy-side caller.

Two more registration behaviours, both new and both load-bearing for
`registry.rs`:

| Call | Result |
| ---- | ------ |
| `POST /v1/agents`, name already in use | **400** `{"detail":"Agent with name s13-dup already exists"}` |
| `PUT /v1/agents/{id}` with `agent_name` + `agent_card_params` | **200**, card updated in place — url changed and the change stuck |
| `PUT /v1/agents/{id}` without `agent_name` | **422** `missing … body.agent_name` |

`re_register_on_card_change` therefore **cannot be a second POST** — a host that
restarts with a changed card would get a 400 and, worse, would look registered.
It must be a PUT (or a DELETE-then-POST). This is a correction to M1's registry.

### The discovery path it *reports* is the legacy `agent.json`

Every call through the proxy starts by fetching the upstream card. When that
fetch fails, the path named in the error is the **legacy** one:

```json
{"jsonrpc":"2.0","id":1,"error":{"code":-32603,"message":"Internal error: Network communication error fetching agent card from http://192.168.215.23:10099/.well-known/agent.json: Cannot connect to host 192.168.215.23:10099 ssl:<ssl.SSLContext object at 0x7fa46d6102d0> [Connect call failed ('192.168.215.23', 10099)]"}}
```

Same string, different address, on the tailnet name:

```json
… "fetching agent card from http://mac-studio.tail86fd19.ts.net:10099/.well-known/agent.json: Cannot connect to host mac-studio.tail86fd19.ts.net:10099 … [Name or service not known]"
```

**What this does and does not establish.** It establishes that the proxy fetches
the upstream card *on the call path*, lazily — not at registration, which is why
registration succeeds against a host that is down. It does **not** establish that
`agent.json` is the only path it tries: the error names the last or the
preferred attempt, and a proxy that tries `agent-card.json` first and
`agent.json` second would report the same thing. We could not settle it, because
the container never reached the agent at any address (below), so no attempt got
far enough to see a 404 on one path and a 200 on the other.

The safe reading, and the cheap fix: our server, like a2a-server-lf 0.4.4,
serves **only** `/.well-known/agent-card.json`, and `agent.json` is a **404** on
it. If LiteLLM does need that path, a proxied call fails on card fetch even with
the host reachable; if it does not, serving it costs one route. Note that A2A
0.3's `agent.json` is a *different document* — flat, `url` at the top level,
`preferredTransport` — so it is a second projection of the catalogue to assemble
and keep true, not an alias. See follow-ups; it is worth confirming with a
reachable host before writing it.

### Reachability, measured in passing ([S9](S9.md))

Three addresses, three different failures — and the difference is S9's whole
question:

| Card `url` | What the container did |
| ---------- | ---------------------- |
| `http://mac-studio.tail86fd19.ts.net:10099` | `[Name or service not known]` — no tailnet DNS in the container |
| `http://192.168.215.23:10099` | `[Connect call failed]` — resolved, TCP refused/unreachable (sandbox bridge) |
| `http://100.72.205.65:10099` (the agent's own tailnet IP) | **hung** — the proxied call never returned (`HTTP 000` at 30s), our server logged no request at all. A dropped SYN, not a refusal. |

So: **not at any address tried, and not for one reason.** The card's `url` must
be an address the container can open a socket to — the DSM host's own tailnet
address, the Docker bridge gateway, or the agent published on the NAS host
network. That is S9's decision and it needs the NAS shell. This spike has
narrowed it usefully: the obstacle is **routing, not DNS alone** (an IP failed
too), and a wrong `url` fails as a *hang* on the caller's side, not an error —
which is itself worth knowing for M1's timeout behaviour.

## The card model: two independent hard failures

`a2a-lf` 0.3.1 cannot deserialize LiteLLM 1.103.0's card. The interesting part is
*how*: not "mostly readable", but two independent hard errors, in a ladder. Each
test in `tests/litellm_card.rs` removes exactly one incompatibility and names the
next.

| # | Incompatibility | Error |
| - | --------------- | ----- |
| 1 | `securitySchemes` is OpenAPI-flavoured — `{"LiteLLMKey":{"type":"http","scheme":"bearer"}}` — but `a2a-lf` models a scheme as a **field-presence union**, `{"httpAuthSecurityScheme":{…}}`, and errors on anything else | contains `security scheme` |
| 2 | `AgentCard.description` has **no serde default** in `a2a-lf`, so it is required; LiteLLM's card has no `description` at all | `missing field \`description\`` |

Patch both, and the overlapping half parses cleanly: `name`, `version` `"1.0.0"`,
`skills[0].id` `"chat"`, `provider.organization` `"LiteLLM Proxy"`, and
`supportedInterfaces[0]` `{url == LiteLLM's top-level url, protocolVersion
"1.0", protocolBinding "JSONRPC"}`.

Note the last one: LiteLLM emits a **superset**. It carries the 0.3-style
top-level `url`, which `a2a-lf` has no field for, *and* a 1.0
`supportedInterfaces` that points at the same address. A reader that only looks
at interfaces still finds the agent. That is why "registration works" is not
evidence the card was read, and why the assertion must be on `skills`.

And the small one, worth pinning because it is a *vocabulary* difference and not
a bug: **LiteLLM says `"text"`, this project says `"text/plain"`.** Nothing reads
the field today; a caller that filtered on input modes would see two words for
one idea.

## The `A2A-Version` header is decorative

Not originally S13's question — it fell out of running a caller against the real
server, and it is [S7](S7.md)'s answer, so it is recorded there rather than here.
The short version: a2a-server-lf 0.4.4 **never reads it**, so nothing a client
sends or omits can break anything. It exists only as a constant in `a2a-lf`.
Consequence for M1: the plan's "if the SDK requires the header, LiteLLM may not
send one" risk is **void** — but so is the expectation that a wrong version fails
cleanly. If we want that, we add it; the SDK will not.

## What this changes

1. **Serve `/.well-known/agent.json`, and confirm first that it is needed.**
   The proxy's card-fetch errors name the legacy path; whether it *also* tries
   `agent-card.json` is unmeasured, and we could not measure it because the
   container could not reach the agent at all. Serving both is the cheap hedge,
   but the 0.3 card is a different document, so it is a second projection of the
   catalogue plus its own hash and its own tests. Confirm against a reachable
   host before writing it — this is the one follow-up that is speculative.
2. **Re-register with PUT, not POST.** `POST /v1/agents` 400s on a duplicate
   name, so a host whose card changed would fail to update while appearing
   registered. `registry.rs`'s `re_register_on_card_change` must PUT.
3. **Do not adopt LiteLLM's card type, and do not hand-roll a second card
   reader.** We never *consume* a LiteLLM card — we serve ours and store an id.
   The committed fixture plus the four tests in `tests/litellm_card.rs` are the
   regression net, so the day either side moves, CI says so instead of a live
   call failing. Writing a tolerant reader for LiteLLM's dialect would be a
   second wire layer for a document we do not read.
4. **Accept that proxied callers see LiteLLM's card.** Skill *routing* survives
   (`metadata.skillId` is in the body); skill *discovery* does not. If §6.1's
   promise is "a caller can discover what this agent offers", that promise holds
   only for callers that reach the agent directly.

## Why this is not a §12.6 escalation

The trigger is *"a2a-rs and LiteLLM disagree about the wire"*. They do not. The
framing — JSON-RPC 2.0, ProtoJSON method names, SSE `data:` frames, the typed
error envelope, and the SDK's own client driving the SDK's own server — is
compatible, proved end to end on the loopback half. What disagrees is (a) **card
schema defaults**, a document we publish and LiteLLM reshapes, and (b) **the
discovery path**, a second route to serve. Both are absorbed on our side. Neither
changes the SDK choice, the pin, or the integration topology, so no escalation.

The one thing that *would* flip this is if M2 or later needs to **consume** a
foreign LiteLLM card — chaining agents, or reading a peer's capabilities. Then
(a) becomes a real dialect problem and "which side moves" is a genuine question.
Nothing in M1 needs it.

## Verdict

**PASS.** The pinned crates and LiteLLM agree on the wire: card at the well-known
path, bearer-auth'd `POST /`, `SendMessage` / `SendStreamingMessage` with SSE, the
typed error envelope, unknown-skill and unknown-method refusals that are
diagnosable rather than confusing. LiteLLM accepts our registration and lists the
agent. What does not carry across is the *card* — LiteLLM synthesises its own,
and its proxy will not fetch a card through an address it cannot route to — and
both are our work to do, not a reason to move a pin. Not a §12.6 escalation.
M1's exit is unblocked on the framing question, with the three follow-ups above
added to M1 rather than
deferred.
