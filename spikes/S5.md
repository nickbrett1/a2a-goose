# S5 — Does `DELETE /v1/agents/{id}` 404 on an already-deleted id?

**Plan (§4):** *Call twice against the live proxy.* **Gates the sweeper's guard
#3**: "404 on delete = success. The sweeper races clean-shutdown deregisters and
must not churn."

## Method

Against the live proxy (`nas:4000`, master key from the environment), with an
agent that is obviously a probe:

```
POST   /v1/agents          {"agent_name":"s5-spike-probe", agent_card_params:{url:"http://127.0.0.1:19999", protocolVersion:"1.0"}}
DELETE /v1/agents/{id}     # it exists
DELETE /v1/agents/{id}     # it is gone
DELETE /v1/agents/{unknown-uuid}
```

## Evidence

| Call | HTTP | Body |
| ---- | ---- | ---- |
| `POST /v1/agents` | **200** | `{"agent_id":"79b5975c-…","agent_name":"s5-spike-probe", …}` |
| `DELETE` #1 | **200** | `{"message":"Agent 79b5975c-… deleted successfully"}` |
| `DELETE` #2 | **404** | `{"detail":"Agent with ID 79b5975c-… not found in DB."}` |
| `DELETE` #3 (unrelated uuid) | **404** | `{"detail":"Agent with ID 00000000-… not found in DB."}` |

`GET /v1/agents` was `[]` before and `[]` after, so the probe left nothing
behind.

## Verdict

**PASS.** An already-deleted id is a 404, indistinguishable from an unknown id.
Guard #3 holds: the sweeper treats 404-on-delete as success, so a race with a
clean-shutdown deregister converges instead of churning.

## A second finding, for M1

The `POST` response is **not** the card we sent. We registered only
`{name, url, protocolVersion}` for a URL nothing listens on, and LiteLLM
returned a synthesised card:

```json
"agent_card_params": {
  "url": "http://127.0.0.1:19999",
  "skills": [{"id": "chat", "name": "Chat", "tags": ["chat"], "description": "Conversational interaction with the agent."}],
  "provider": {"url": "http://nas:4000", "organization": "LiteLLM Proxy"},
  "supportedInterfaces": [{"url": "http://nas:4000/a2a/79b5975c-…", "protocolBinding": "JSONRPC", "protocolVersion": "1.0"}],
  …}
```

So the upstream fetch from `/.well-known/agent-card.json` is **not** on the POST
path: LiteLLM answers immediately with its own defaults and fills in the real
card later (or not at all, if the URL is unreachable). Two consequences for M1:

- "the agent appears in `GET /v1/agents`" is not evidence that LiteLLM read our
  card. M1's test has to assert on the **skills**, not on the agent existing.
- Registration is best-effort even when it succeeds: a node agent that registers
  while its own card endpoint is still starting up can be pinned with a default
  card until the next re-registration (§6.2's card-hash path).
