# S2 — Does goose forward `X-LiteLLM-Trace-Id` to its provider calls?

**Plan (§4):** *Start a local HTTP proxy that logs upstream request headers, point
goose at it, run one prompt, and check whether a per-session trace id reaches
LiteLLM.* **Highest-leverage spike in the plan.** It gates §6.7 (registering each
node agent with `require_trace_id_on_calls_by_agent` and `max_budget_per_session`)
and §11 open question 1.

This is also an **explicit §12.6 escalation trigger**: *"S2 fails (cost control
changes shape)."* So the deliverable here is a verdict **and a stop**.

## Why it matters

LiteLLM budgets are per-*iteration-budget* — you attach
`max_iterations` / `max_budget_per_session` to an **agent** and LiteLLM enforces
them by correlating every provider call to that agent through a trace id sent on
the provider request. goose is the thing that actually calls the provider, so the
only way to tag goose's calls with *our* per-thread trace id is for our node
agent to give goose a per-session id that goose forwards upstream. If goose
cannot forward a per-session header, there is nothing to key a per-thread budget
on and §6.7 collapses to per-key budgets.

## Method

Three probes, in increasing order of hope:

1. **Static header.** Is there any goose setting that adds headers to its
   provider calls, and do they arrive?
2. **Per-session header.** goose already sends a per-session `agent-session-id`
   upstream. Can it be *renamed* to `x-litellm-trace-id`?
3. **Configurable provider.** Does a declarative custom provider
   (`~/.config/goose/custom_providers/*.json`) accept a header override?

Harness: a threading HTTP proxy (`/tmp/headerlog_proxy.py`) on `127.0.0.1:4010`
in front of the live proxy (`http://nas:4000`), logging every request's headers to
`/tmp/s2-headers.log`, and used as goose's `OPENAI_HOST`.

## Evidence

### 1. Static headers — forwarded, but constant

`LITELLM_CUSTOM_HEADERS` (goose's env passthrough for OpenAI-compatible
providers) **does** reach upstream. Every `POST /v1/chat/completions` arriving at
the proxy carried:

```
x-litellm-trace-id: trace-s2-static
x-spike-test: hello
agent-session-id: 20260916_7
```

So goose forwards custom headers, but they are **static per process** — the same
value on every call, for every session. A static id cannot distinguish two
concurrent threads, so it cannot carry a per-thread budget.

### 2. Per-session id — exists, but not renameable at 1.50.0

goose *does* send a genuine per-session header, `agent-session-id`. If it could be
renamed to `x-litellm-trace-id`, S2 would pass. It cannot:

```
$ grep -rn "session_id_header_override" <goose>     # main / goose-providers
…/goose-providers/src/declarative.rs:  session_id_header_override …
$ grep -rn "session_id_header_override" <goose@v1.50.0>
$ grep -rn "session_id_header_override" <goose@v1.50.1>
(no matches — count 0 in both tags)
```

The setting landed **after** 1.50.x. The deployed hosts run 1.50.0.

### 3. Declarative provider with the override — silently ignored

Configured `~/.config/goose/custom_providers/s2trace.json`:

```json
{
  "name": "s2trace", "engine": "openai",
  "api_key_env": "LITELLM_API_KEY",
  "base_url": "http://127.0.0.1:4010/v1",
  "session_id_header_override": "x-litellm-trace-id",
  "dynamic_models": true,
  "supports_streaming": true,
  "models": [{"name": "deepseek-v4-flash", "context_limit": 200000}]
}
```

Result: goose accepted the provider, called the proxy, and sent
`agent-session-id: 20260916_7` — **with `x-litellm-trace-id` absent entirely**.
The unknown key is not an error at 1.50.0; it is dropped. A silently-ignored
setting is worse than a rejected one, because it looks configured.

## Verdict

**FAIL as specified.** At goose 1.50.x there is no way to get a *per-session*
identifier into a header named `x-litellm-trace-id`. Headers can be added but only
statically; the one per-session identifier goose sends cannot be renamed; and the
setting that would rename it does not exist in 1.50.0.

Therefore **§6.7 as written is not implementable on goose 1.50.0**, and with it
the per-thread half of §6.7 (`require_trace_id_on_calls_by_agent` +
`max_budget_per_session` keyed on a thread).

## 🚩 Escalation (§12.6) — needs a decision

This is the trigger *"S2 fails (cost control changes shape)"*. Per §12.6 the
correct action is to **stop and ask**, not to invent a workaround. The options,
with what each costs:

| Option | What it buys | What it costs |
| ------ | ------------ | ------------- |
| **A. Per-key budgets (recommended)** | Works today; a hard ceiling on total spend; no goose change | No per-*thread* accounting — a runaway thread can eat the whole key's budget. Node agents need one key each to be separately capped. |
| **B. Wait for a goose release ≥ the `session_id_header_override` commit** | §6.7 exactly as written | Blocks cost control on an upstream release; the deployed 1.50.0 would have to be upgraded on both hosts; no ETA |
| **C. Our agent sends the id out-of-band** (e.g. one LiteLLM key **per node agent**, and let LiteLLM's own `agent-session-id` be the correlation) | Per-thread visibility in LiteLLM logs without trusting a forwarded header | Correlation lives in LiteLLM's logs, not its budget engine; budgets still per-key |
| **D. Pre-1.50.0 patch/build of goose with the setting backported** | Unblocks at 1.50.0 | Violates hard constraint #8 in spirit (we do not own goose's build) and diverges the hosts from a released goose |

**Recommendation: A.** It is the only option that is implementable today, keeps
the node agent honest (one key per agent, so "which agent spent this" is
answerable), and does not couple Phase 1 to an upstream release. B remains the
right answer *later*, as an upgrade, not a blocker now.

**Until a decision is recorded, §6.7's per-thread budgeting is out of scope for
M1 and the registry client should register agents *without*
`require_trace_id_on_calls_by_agent`.**

## Consequences to fold back into the plan

- §6.7 — per-thread budgets are blocked at 1.50.x; default to per-key, revisit on
  a goose upgrade. Registry registration must not depend on a trace id.
- §11 open question 1 — answered: no, goose 1.50.x cannot carry a per-session
  trace id. Record the answer and close the question.
- The liveness of "which session spent this" moves from LiteLLM's budget engine
  to **one LiteLLM key per node agent**. That is a change to §6.7's shape and
  should be reflected in the config example's `registry` block.
- Do **not** ship the `s2trace.json` experiment (`~/.config/goose/custom_providers/`)
  on the hosts; it is spike scaffolding and a silently-ignored setting.
