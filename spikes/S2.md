# S2 — Does goose forward `X-LiteLLM-Trace-Id` to its provider calls?

**Plan (§4):** *Start a local HTTP proxy that logs upstream request headers, point
goose at it, run one prompt, and check whether a per-session trace id reaches
LiteLLM.* **Highest-leverage spike in the plan.** It gates §6.7 (registering each
node agent with `require_trace_id_on_calls_by_agent` and `max_budget_per_session`)
and §11 open question 1.

This is also an **explicit §12.6 escalation trigger**: *"S2 fails (cost control
changes shape)."* So the deliverable here is a verdict **and a stop**.

## Why it matters

LiteLLM budgets are per-*iteration-budget* — you attach
`max_iterations` / `max_budget_per_session` to an **agent** and LiteLLM enforces
them by correlating every provider call to that agent through a trace id sent on
the provider request. goose is the thing that actually calls the provider, so the
only way to tag goose's calls with *our* per-thread trace id is for our node
agent to give goose a per-session id that goose forwards upstream. If goose
cannot forward a per-session header, there is nothing to key a per-thread budget
on and §6.7 collapses to per-key budgets.

## Method

Three probes, in increasing order of hope:

1. **Static header.** Is there any goose setting that adds headers to its
   provider calls, and do they arrive?
2. **Per-session header.** goose already sends a per-session `agent-session-id`
   upstream. Can it be *renamed* to `x-litellm-trace-id`?
3. **Configurable provider.** Does a declarative custom provider
   (`~/.config/goose/custom_providers/*.json`) accept a header override?

Harness: a threading HTTP proxy (`/tmp/headerlog_proxy.py`) on `127.0.0.1:4010`
in front of the live proxy (`http://nas:4000`), logging every request's headers to
`/tmp/s2-headers.log`, and used as goose's `OPENAI_HOST`.

## Evidence

### 1. Static headers — forwarded, but constant

`LITELLM_CUSTOM_HEADERS` (goose's env passthrough for OpenAI-compatible
providers) **does** reach upstream. Every `POST /v1/chat/completions` arriving at
the proxy carried:

```
x-litellm-trace-id: trace-s2-static
x-spike-test: hello
agent-session-id: 20260916_7
```

So goose forwards custom headers, but they are **static per process** — the same
value on every call, for every session. A static id cannot distinguish two
concurrent threads, so it cannot carry a per-thread budget.

### 2. Per-session id — exists, but not renameable at 1.50.0

goose *does* send a genuine per-session header, `agent-session-id`. If it could be
renamed to `x-litellm-trace-id`, S2 would pass. It cannot:

```
$ grep -rn "session_id_header_override" <goose>     # main / goose-providers
…/goose-providers/src/declarative.rs:  session_id_header_override …
$ grep -rn "session_id_header_override" <goose@v1.50.0>
$ grep -rn "session_id_header_override" <goose@v1.50.1>
(no matches — count 0 in both tags)
```

The setting landed **after** 1.50.x. The deployed hosts run 1.50.0.

### 3. Declarative provider with the override — silently ignored

Configured `~/.config/goose/custom_providers/s2trace.json`:

```json
{
  "name": "s2trace", "engine": "openai",
  "api_key_env": "LITELLM_API_KEY",
  "base_url": "http://127.0.0.1:4010/v1",
  "session_id_header_override": "x-litellm-trace-id",
  "dynamic_models": true,
  "supports_streaming": true,
  "models": [{"name": "deepseek-v4-flash", "context_limit": 200000}]
}
```

Result: goose accepted the provider, called the proxy, and sent
`agent-session-id: 20260916_7` — **with `x-litellm-trace-id` absent entirely**.
The unknown key is not an error at 1.50.0; it is dropped. A silently-ignored
setting is worse than a rejected one, because it looks configured.

## Verdict

**FAIL as specified.** At goose 1.50.x there is no way to get a *per-session*
identifier into a header named `x-litellm-trace-id`. Headers can be added but only
statically; the one per-session identifier goose sends cannot be renamed; and the
setting that would rename it does not exist in 1.50.0.

Therefore **§6.7 as written is not implementable on goose 1.50.0**, and with it
the per-thread half of §6.7 (`require_trace_id_on_calls_by_agent` +
`max_budget_per_session` keyed on a thread).

## 🚩 Escalation (§12.6) — needs a decision

This is the trigger *"S2 fails (cost control changes shape)"*. Per §12.6 the
correct action is to **stop and ask**, not to invent a workaround. The options,
with what each costs:

| Option | What it buys | What it costs |
| ------ | ------------ | ------------- |
| **A. Per-key budgets (recommended)** | Works today; a hard ceiling on total spend; no goose change | No per-*thread* accounting — a runaway thread can eat the whole key's budget. Node agents need one key each to be separately capped. |
| **B. Wait for a goose release ≥ the `session_id_header_override` commit** | §6.7 exactly as written | Blocks cost control on an upstream release; the deployed 1.50.0 would have to be upgraded on both hosts; no ETA |
| **C. Our agent sends the id out-of-band** (e.g. one LiteLLM key **per node agent**, and let LiteLLM's own `agent-session-id` be the correlation) | Per-thread visibility in LiteLLM logs without trusting a forwarded header | Correlation lives in LiteLLM's logs, not its budget engine; budgets still per-key |
| **D. Pre-1.50.0 patch/build of goose with the setting backported** | Unblocks at 1.50.0 | Violates hard constraint #8 in spirit (we do not own goose's build) and diverges the hosts from a released goose |

**Recommendation: A.** It is the only option that is implementable today, keeps
the node agent honest (one key per agent, so "which agent spent this" is
answerable), and does not couple Phase 1 to an upstream release. B remains the
right answer *later*, as an upgrade, not a blocker now.

**Until a decision is recorded, §6.7's per-thread budgeting is out of scope for
M1 and the registry client should register agents *without*
`require_trace_id_on_calls_by_agent`.**

## Consequences to fold back into the plan

- §6.7 — per-thread budgets are blocked at 1.50.x; default to per-key, revisit on
  a goose upgrade. Registry registration must not depend on a trace id.
- §11 open question 1 — answered: no, goose 1.50.x cannot carry a per-session
  trace id. Record the answer and close the question.
- The liveness of "which session spent this" moves from LiteLLM's budget engine
  to **one LiteLLM key per node agent**. That is a change to §6.7's shape and
  should be reflected in the config example's `registry` block.
- Do **not** ship the `s2trace.json` experiment (`~/.config/goose/custom_providers/`)
  on the hosts; it is spike scaffolding and a silently-ignored setting.

# The decision (recorded 2026-09-16, owner: Nick)

Asked the owner *"where are budgets managed, I don't do that today?"* — so
before deciding anything, the second half of S2 was run: **find out what the
deployed proxy can actually do.** The answer changed the decision, because the
plan's premise was wrong in a way that helped us.

## Where budgets would be managed (and where they are today)

**LiteLLM** — the same proxy goose already calls. It is the only place in this
system that sees every provider call, so it is the only place a ceiling can be
enforced *below* the agent. What it has, verified against `nas:4000`
(**LiteLLM 1.103.0**):

| Surface | Endpoint | State today |
| ------- | -------- | ----------- |
| Budget objects | `POST /budget/new`, `/budget/list`, `/budget/delete`, `GET /management/v1/budgets` | **`[]` — none exist** |
| Virtual keys | `/key/generate`, `/key/list` | **`{"keys":[],"total_count":0}` — zero keys** |
| Per-user cap | `GET /user/info` | `default_user_id`, **`max_budget: null`**, `spend: 133.14` |
| Teams / orgs | `/team/...`, `/organization/...` | none |
| Spend logs | `/spend/logs`, `/global/spend/models` | **working** — per day, per model, per user |
| Reports | `/global/spend/report` | **400, Enterprise only** |

So: **nothing is capped today, and every call runs on the master key.** The
spend logs show `litellm_proxy_master_key` as the key on every row, which is
what "one shared key, no attribution" looks like from the proxy's side.

A `POST /budget/new` probe (created, read back, deleted) confirms the mechanism
works on this build:

```json
{"budget_id":"s2-probe-budget","max_budget":20.0,"soft_budget":15.0,
 "tpm_limit":200000,"rpm_limit":60,"budget_duration":"30d",
 "budget_reset_at":"2026-10-01T00:00:00Z", …}
```

Two things worth knowing: `budget_duration: "30d"` does **not** mean
now+30d — `budget_reset_at` snapped to the **start of the next calendar month**
(`2026-10-01T00:00:00Z`), so a window is "the rest of the month", not a rolling
30. And `soft_budget` is the one that fires an alert **without** failing the
call, which is the sane default for a first ceiling.

## The plan's §6.7 fields do not exist on this build

This is the finding that makes S2 worse than "the header can't be sent". The
agent object returned by `GET /v1/agents` on 1.103.0 is:

```
agent_id, agent_name, agent_card_params, created_at/by, updated_at/by,
litellm_params, object_permission, spend, tpm_limit, rpm_limit,
session_tpm_limit, session_rpm_limit, static_headers, extra_headers, keys
```

`max_iterations`, `max_budget_per_session` and
`require_trace_id_on_calls_by_agent` were **POSTed and silently dropped** —
they are absent from the response and from the stored row. §6.7 was written
against LiteLLM docs that do not match the deployed version.

What the agent object *does* have that matters: a per-agent **`spend`** field,
and **`session_tpm_limit` / `session_rpm_limit`** — per-session rate limits on
the agent. Not budgets, but real controls that §6.7 did not know about.

## Decision

**Adopt option A+C, and move the primary control into our own agent.**

1. **Primary: the node agent enforces its own limits.** Spikes S4 and S6 showed
   the ACP stream already carries `usage_update` (`used`/`size` per session) and
   every turn returns `stopReason` plus a `usage` block — and S6 showed
   `session/close` is available. So max-iterations-per-task,
   max-concurrent-sessions, and a token/wall-clock ceiling per context are all
   enforceable **locally**, with no LiteLLM cooperation and no goose change.
   This is a stronger control than §6.7 asked for: §6.7 throttled goose's
   *provider calls* after the fact, whereas this stops the *turn*. It is also
   the only control that survives the LiteLLM side being misconfigured.

2. **Backstop: one virtual key per node agent, with a Budget object attached.**
   `max_budget` hard, `soft_budget` for the alert-first phase,
   `budget_duration: "30d"` (read: monthly reset). Greenfield — zero keys exist
   today — so there is no migration and no risk of capping something already in
   use. A key per node agent also buys the attribution the trace header was
   supposed to provide: `/spend/logs` already splits by key, so "which node
   spent this" becomes answerable without goose changing at all.

3. **Per-thread budgets: dropped from Phase 1.** §6.7's per-thread half is not
   implementable on goose 1.50.x (no per-session header) *or* on LiteLLM
   1.103.0 (no such agent fields). Revisit only if a goose upgrade ships
   `session_id_header_override` **and** we still want per-thread enforcement in
   the proxy rather than in the agent.

4. **Attribution: meter it ourselves, don't ask goose to forward an id.**
   Token counts arrive in the ACP stream for free (`usage_update`, and the
   `usage` block on every prompt reply), so per-thread cost can be recorded
   against our own `contextId` in the SQLite map beside contextId→sessionId.
   That is the honest version of what the trace id was for. Note that
   `/global/spend/report` is Enterprise-gated, so **do not design around
   LiteLLM's reporting UI** — our own numbers are the durable ones.

5. **Do not register agents with a trace-id requirement.** Registry
   registration must not depend on a field the proxy drops.

### What this costs

Today's actual spend is ~$105–133/30d, almost entirely
`deepseek/deepseek-v4-flash`. So the ceilings are cheap to set and cheap to
raise: a `max_budget` in the single-digit-to-low-double-digit dollars per node
agent per month, with `soft_budget` ~75% of it, is proportionate. The point of
the ceiling is to bound a bug, not to ration normal use.

### Consequences folded back into the plan

- §6.7 — rewritten as above: local limits primary, per-key budget backstop,
  per-thread dropped.
- §6.7's registry registration — drop `require_trace_id_on_calls_by_agent`,
  `max_iterations` and `max_budget_per_session`; they are dropped on POST.
- §11 open question 1 — **closed**: no, and it is not needed.
- The config example's `registry` block now carries the per-agent key and the
  budget shape (see `config/config.example.yaml`).

# Correction (2026-09-16, later the same day)

The owner pushed back on the decision above: *"I don't need budgets per agent, I
doubt they can account correctly either."* So the accounting was tested rather
than argued about. **The owner is right, and one of my own claims was wrong.**

## Test: one known turn, accounted on both sides

One trivial A2A turn — `session/new`, then "What is 2+2? Reply with just the
number." — against the deployed goose, with LiteLLM's request logs read for the
exact window.

| | goose's ACP stream | LiteLLM's logs |
| --- | --- | --- |
| input tokens | **34001** | **34001** (call 2 of 2) |
| output tokens | 10 | 10 |
| cost | **$0.0001266776** | **$0.000438888** |
| provider calls seen | *n/a* | **2** |

The two calls LiteLLM logged were `p=429 c=90` and `p=34001 c=10`. Two
conclusions, and they point in opposite directions from where I expected:

1. **Token accounting is exact and agrees.** 34001 = 34001. LiteLLM is not
   guessing token counts; it reads them off the provider response. My suspicion
   that the accounting "can't be right" does not survive contact with the data.

2. **Dollar accounting is a local price table, and there are two of them.**
   goose and LiteLLM price the *same* call **3.5x apart** ($0.0001267 vs
   $0.0004389), and neither is the provider's invoice. A budget in LiteLLM is
   therefore enforced against LiteLLM's opinion of the price — monotonic in
   usage and conservative, so adequate as a *ceiling*, but it is not accounting
   and should never be read as "what this cost".

3. **One A2A turn is not one provider call.** The turn fanned out into two
   completions, and the smaller one (429 in / 90 out — goose's own overhead) is
   **invisible in the ACP `usage` block**. So the ACP stream cannot see the whole
   cost of a turn either.

## My own error, corrected

The decision above claimed we could meter cost ourselves from `usage_update`.
**That was wrong** — and the reason is worth recording:

- `usage_update` *does* carry a cost estimate
  (`{"cost": {"amount": 0.0001266776, "currency": "USD"}}`). The committed
  fixture `tests/fixtures/acp-turn.jsonl` **does not show this field**, because
  it was dropped as volatile when the transcript was sanitised. Tests must
  therefore not assert its absence.
- But it is goose's *estimate*, it covers only the main call, and it misses the
  per-turn overhead calls. It is a trend line, not a bill.

## Revised decision

- **Per-agent budget and per-agent key: dropped.** Not merely deferred — the
  justification is gone. A ceiling priced by a third party's local table, on a
  system that today spends ~$0.0004 per trivial turn, is unearned ceremony. If a
  ceiling is ever wanted, the honest place is the **provider account** (a hard
  limit at the DeepSeek/Google end), not a proxy that guesses the price.
- **Local metering measures behaviour, not money.** Keep max-iterations,
  max-concurrent-sessions, token/context ceiling and wall-clock — these are
  exact, they are ours, and they are what actually stops a runaway loop. Do
  **not** attach a dollar figure to them.
- **Spend stays where it already works: LiteLLM's logs**, read after the fact
  for audit. Two traps found the hard way: `start_date == end_date` returns
  **zero** rows for a day that has thousands (the window is half-open), and
  `/global/spend/report` is Enterprise-gated, so any reporting must be built on
  `/spend/logs/v2`, which gives per-request token counts.

So the honest summary of S2: **the transport gap was real, the accounting gap
was not, and the cost-control design in §6.7 was answering a question nobody had
asked.** Bound the loop, not the wallet.
