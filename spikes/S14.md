# S14 — Does the agent really own `goose serve`?

**Plan (§4, revised):** the deploy tree used to ship one unit — the launcher's —
and *nothing* started `goose serve`. On reboot the agent came back, served a
card, accepted calls, and failed every turn on `connection refused` to
`:3284`: a healthy-looking agent that could not answer. The direction is now that
the **agent** starts goose as a child, restarts it when it dies, and refuses to
start if something is already serving on the ACP address. *Does that actually
work, against a real goose?*

The plan-level question this replaces — "which unit starts goose?" — is answered
by not having one: there is one restart mechanism per level. goose is the agent's
child; the agent is launchd's (or DSM's) job.

## Method

Three layers, each cheap enough to run every time:

1. **Unit/config tests** (`cargo test`) for everything that is a *decision*:
   which invocation is built, which configurations are refused, when a restart
   is attempted and when it is given up on. These run against a shell script
   standing in for goose, and against injected readiness probes, so they are
   deterministic and take about a second — and `scripts/mutations.py` breaks
   seven of those decisions on purpose (adopt the occupied address, skip the
   readiness gate, `SIGKILL` instead of asking, and so on) and requires the
   matching test to fail, because a test that has never been seen to fail is not
   evidence.
2. **A live end-to-end run** on this box against a real `goose 1.50.0`
   (`/tmp/e2e-own.sh`): boot the agent owning a goose on `:3399`, take a real
   turn, `kill -9` the goose, take a second turn, start a second agent on the
   same address, then `SIGTERM` the first.
3. **The host-relevant leftovers**: what happens to goose on an ordinary stop,
   and what a *user* asking `/status` is told while all of this happens.

## Evidence — the agent starts it, and says so

Nothing was started by hand; the only goose on `:3399` is the agent's child.

```
$ ./target/debug/a2a-goose --config /tmp/e2e-own.yaml &
$ curl -sS localhost:10099/status | jq .acp
{"state":"idle", "url":"http://127.0.0.1:3399/acp", "secretSet": true,
 "serve":{"mode":"own", "managed":true, "state":"ready",
          "pid":1778556, "restarts":0}}

$ ps -o pid,ppid,args --ppid <agent-pid>
1778556 1778531 /home/node/.local/bin/goose serve --host 127.0.0.1 --port 3399
```

The argument list is the point: `serve --host 127.0.0.1 --port 3399` and nothing
else — the *address the config dials*, so `goose.acp.url` and the child's
listener cannot drift apart, and the bare invocation [S1](S1.md) pinned
(`--platform cli`, no `--enable-scheduler`).

## Evidence — it refuses to start when goose cannot

The agent checks the address before it binds its own port, and the check is a
*dial*, not a `bind`: it distinguishes "nothing is there" from "a goose is
already there" from "something else is there".

| Configuration | Result |
| ------------- | ------ |
| nothing on the address | spawns goose, waits for `initialize`, then binds |
| a real goose already serving | **refused** — `exit 1`, before binding |
| a listener that is not goose | **refused**, and the refusal says so (`did not answer an ACP initialize`) |
| no key in the env, `unauthenticated: false` | **refused** — goose's own reason is quoted back |
| a key *and* `unauthenticated: true` | **refused** — a configuration that lies about what it is protecting |
| goose exits 7 before answering | **refused**, with the child's own stderr in the message |
| goose comes up but never answers | **refused** after the initialize deadline, and the child is `SIGTERM`ed rather than left holding the port |

The live run's own words, from a second agent pointed at the first one's goose:

```
{"level":"ERROR","fields":{"message":"refusing to start",
 "error":"http://127.0.0.1:3399 is already in use: something is listening there
 and it answered an ACP `initialize`, so it is almost certainly the goose serve
 this host already runs. This agent starts and owns its own `goose serve` and
 will not adopt a server it did not start - two of them share one sessions.db and
 one set of recipes, and a turn could not say which one it landed on. Stop it, or
 set goose.acp.serve to \"external\" if that server is yours to manage"}}
$ echo $?
1
```

## Evidence — a crash is a restart, and the agent stays up

```
$ kill -9 1778556                      # the goose, under the agent
{"level":"WARN","fields":{"message":"restarting goose serve","attempt":1,
 "delay_ms":1000}}
{"level":"INFO","fields":{"message":"goose serve is answering again",
 "pid":1778646,"address":"http://127.0.0.1:3399"}}
```

`ps` shows one goose, a new pid; `/status` reads `restarts: 1` and `state:
ready`; the agent's own pid never changed, and a second real turn on the
restarted goose returns `TASK_STATE_COMPLETED`.

The first turn after a restart pays one extra cost, and the log says why:

```
{"level":"INFO","fields":{"message":"the ACP connection has ended (goose
 restarted?): reconnecting, which starts a fresh session per context - the
 conversation stays in goose's own sessions.db, but the model does not carry it
 into the new session"}}
{"level":"INFO","fields":{"message":"discarded the session pool along with its
 connection","sessions":1}}
```

The signal is the connection-level SSE stream ending — the one thing goose does
tell us when it goes away. Without it the agent kept reusing a connection id the
new goose had never heard of, and every turn after a restart was a `404` (this
was seen in the first live run). Losing the *session label* is the price; losing
the *conversation* is not, because it is in goose's `sessions.db`.

Restarts are bounded, and the bound is the loop, not a number of tries: 1s
doubling to 30s, and more than **5 exits in a 60s window** is a give-up that
exits the agent non-zero so the init system restarts the whole thing — with the
decision made in the process rather than by an init unit that would have to be
taught the same policy.

## Evidence — an ordinary stop takes goose with it

```
$ kill -TERM <agent-pid>
{"level":"INFO","fields":{"message":"SIGTERM: shutting down"}}
{"level":"INFO","fields":{"message":"stopped the goose serve this agent started",
 "pid":1778646}}
$ pgrep -f 'goose serve --host 127.0.0.1 --port 3399'   # nothing
```

`SIGTERM` first, `SIGKILL` if it is still there after five seconds, and the child
is spawned with `kill_on_drop` as the backstop for a path that unwinds instead of
returning.

## Verdict

**PASS on this box, against goose 1.50.0** — for start, the readiness gate, the
key, the crash-and-restart, the conflict refusal and a clean stop.
`cargo test` covers the same set deterministically (7 tests in
`tests/serve_supervision.rs`, plus the config refusals); the ignored live test
runs them against a real goose. The same seven pass on the **macOS** build agent
(`cargo test --locked`, Buildkite build 41) — so the process-level parts of this
(answer the child, `SIGTERM` it, wait for it, take the port decision) are not a
Linux-only result. What is still untested on darwin is the *goose* half: nothing
has started a Darwin goose.

**What this does NOT prove**, and what unblocks each:

| Unproven | Why it matters | Blocked on |
| -------- | -------------- | ---------- |
| the same thing on **darwin** (Mac Studio) | the tests pass there, but nothing has started a *Darwin goose*; `libc::kill`, process groups and launchd's `AbandonProcessGroup` default are the parts still unproven | the Mac, [S12](S12.md) |
| a **`SIGKILL`ed agent** leaving a goose behind | the next boot would refuse to start ("something is already listening there"): loud and correct, but not self-healing | [S8](S8.md) |
| a host whose goose was already running **before** install | the person installing meets the refusal and has to stop it once | [S8](S8.md), [S12](S12.md) |
| `goose.acp.serve: external` on a host that manages its own goose | the escape hatch is implemented and unit-tested; no host uses it | nothing — this is a choice in the config |

## What it changes

- `deploy/` no longer implies that a host start goose, because a host does not:
  the launchd plist and the DSM boot script supervise the **agent**, and the
  agent supervises goose. `deploy/README.md` says so, and the pre-install note
  now asks a returning host to stop any hand-run goose first.
- The ACP address became a **contract** rather than a hint: with
  `serve: own`, `goose.acp.url` must be `http` on an IPv4 loopback with the bare
  `/acp` path, because that is the only thing the agent can start a server on.
  Anywhere else is `serve: external`, and then nothing is spawned and nothing is
  checked — the config has to say which of the two it means.
- The **key became the child's env**: with `serve: own` the agent hands its
  `secretEnv` value to goose as `GOOSE_SERVER__SECRET_KEY`, which is also what it
  sends as `X-Secret-Key`. One secret, one place it is written down.
