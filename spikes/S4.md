# S4 — Does one `goose serve` handle concurrent sessions?

**Plan (§4):** *Drive two sessions at once on a single `goose serve`.* **Gates
§6.3/§6.5**: whether the node agent multiplexes many A2A contexts onto one
connection (cheap, one process) or must fork one `goose serve` per context
(expensive, and a port per thread).

## Method

Harness: `/tmp/s4_probe6.py`. Against one deployed `goose serve` on
`127.0.0.1:3284`:

1. `initialize` → hold the `Acp-Connection-Id`,
2. open the connection-level SSE stream,
3. `session/new` **twice** on the same connection (same valid cwd; see the
   incidental finding),
4. open a **per-session** SSE stream for each (`Acp-Session-Id`),
5. `session/prompt` both sessions **from separate threads at the same time**,
   with distinguishable prompts,
6. check each reply lands on the right stream with the right content.

## Evidence

Two sessions created on one connection; both replies arrived on the
connection-level stream and were correlated by JSON-RPC id:

```
sessions: {102: '20260916_17', 101: '20260916_16'}
```

Two prompts issued concurrently; both POSTs returned immediately (empty body,
202 — the request is fire-and-forget, the reply is on the stream):

```
s1 prompt POST returned in 0.02s body=''
s2 prompt POST returned in 0.00s body=''
[s2] chunk (sid=20260916_17) 'beta'
REPLY id=202 stream=s2 {"stopReason": "end_turn", "usage": {"totalTokens": 34034, "inputTokens": 33996, "outputTokens": 38}}
[s1] chunk (sid=20260916_16) 'alpha'
REPLY id=201 stream=s1 {"stopReason": "end_turn", "usage": {"totalTokens": 33998, "inputTokens": 33996, "outputTokens": 2}}
elapsed 2.0s, replies=2
```

Both turns completed in **2.0s wall clock** — i.e. overlapping, not serialised.
The session streams are properly isolated: `alpha` (session `…16`) arrived only
on stream `s1`, `beta` (session `…17`) only on `s2`, and neither stream saw the
other session's chunk. This is the property that matters: **one shared
connection, N independent conversations, no cross-talk.**

### Incidental finding — goose validates `cwd`

First attempt used `cwd: "/work"` (a path that exists in the fixture's sanitised
world but not on this host). Both `session/new` calls were rejected:

```json
{"jsonrpc":"2.0","id":101,"error":{"code":-32602,"message":"Invalid params","data":"invalid directory path"}}
```

So §6.5's "cwd is the namespace" is **enforced by goose**, not merely by us: a
cwd the agent cannot see is a `-32602`, not a silent default to the server's own
cwd. Good — but it also means the agent must create/validate the per-context
directory *before* `session/new`, and a bad `allowedRoots` entry fails loudly at
the ACP layer.

### Incidental finding — session ids are date+counter

`20260916_16`, `20260916_17` — `<yyyymmdd>_<n>`, monotonic within a day. Opaque
to us (we treat them as strings), but it means ids are **not** globally unique
across a date boundary and give no ordering guarantee across restarts.

## Verdict

**PASS.** One `goose serve` multiplexes concurrent sessions and keeps them
isolated, on one connection, at roughly the cost of the two turns themselves.
The node agent does **not** need a goose process (or a port) per A2A context.

## Consequences for the plan

- **§6.3/§6.5 — one shared ACP connection for all contexts.** The agent holds one
  connection, one connection-level stream, and one per-session stream per live
  session, and demultiplexes by JSON-RPC id (connection scope) and
  `Acp-Session-Id` (session scope). This is the single most complex piece of M1
  and the one to build first.
- **§6.5 — validate cwd before `session/new`.** `allowedRoots` is a real
  enforcement point; a bad path is a hard `-32602`, not a fallback.
- Do not derive identity or ordering from the goose session id
  (`<yyyymmdd>_<n>`). Our own `contextId` stays the identifier; the session id is
  a pointer, and the map is the only thing that gives it meaning.
- S4 was originally listed as "needs a real first"; it did not — it needed only
  the ACP transport from [S3](S3.md). M2 now has no unproven dependency on this.
