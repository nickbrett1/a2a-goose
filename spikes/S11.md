# S11 — Does the emitted launcher resolve the right triple, fail open, and *upgrade*?

**Status: PASS on mac-studio for items 1–3 and 5; item 4 not exercised on a
host.** `scripts/fetch-launch.sh` is generated by genproj (the `fetch-launch`
capability) and is the thing both hosts' supervisors actually run (§8, hard
constraint #14: the *launcher* is supervised, not the agent).

Item 5 was **found broken** on mac-studio (0.1.12 → 0.1.14) and fixed in the
capability ([genproj #28](https://github.com/nickbrett1/genproj/pull/28)) and in
the copy here; mac-studio then ran the fix on a real host through **two real
upgrades** (0.1.14 → 0.1.15 → 0.1.16). Items 1–2 were exercised on mac-studio
(see also `memos/2ivsc8z3XbtkNPoM26SmCg`); item 3 is proven by the env-file tests
in genproj and by mac-studio's own env file. One finding about the launcher is
new and has since been **decided** — see **The supervisor is a git checkout**
below and the decision record at the end.

## What to prove

1. **Triple resolution.** On aarch64-darwin and on DSM's x86_64/aarch64, the
   launcher picks the asset matching the host triple. The vocabulary is the three
   triples in §3: `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`,
   `aarch64-unknown-linux-musl`. The DSM box's `uname -m` is not necessarily
   what the triple expects — prove the mapping, do not assume it.
2. **Fail open.** With `NO_FETCH=1`, and with the network down, the launcher must
   still exec whatever binary it already has rather than refusing to start.
   Fail-open is the whole point: a launchd/Task-Scheduler restart storm must not
   brick the node.
3. **`ENV_FILE`.** The env file is sourced *by the launcher* (not the plist), so
   prove secrets reach the agent without ever appearing in a launchd plist or a
   world-readable file.
4. **Pin/digest.** The downloaded asset is verified (checksum) and the version is
   recorded; a corrupt or truncated download does not become the running binary.
5. **Upgrade.** A host that has already installed a release fetches a *newer* one
   and ends up running it. Its `current` already points at a release directory,
   which is the case every host is in after its first boot — and the case that
   was broken.

## Item 5: the defect (mac-studio, 0.1.12 → 0.1.14)

The flip was:

```bash
ln -sn "${RELEASES_DIR}/${version}" "${DEPLOY_DIR}/.current.$$"
mv -f "${DEPLOY_DIR}/.current.$$" "$CURRENT"
```

`current` is a symlink to a **directory**, so `mv` follows it, decides the
destination is a directory, and moves the new link *inside* the previous release.
`current` is left untouched and a stray `.current.<pid>` appears under the old
version. `mv -T` is the fix on GNU and does not exist on macOS.

Reproduced in isolation:

```
before:                             releases/0.1.14
after mv -f .current.$$ current:    releases/0.1.14     # unchanged
stray:                              ./releases/0.1.14/.current.1831371
ln -sfn variant:                    releases/0.1.15     # correct
```

Live, on mac-studio, after the 0.1.12 → 0.1.14 upgrade: the launcher logged
`installed 0.1.14`, `lsof -p <pid> txt` still named
`.../releases/0.1.12/bin/a2a-goose`, and the evidence was a
`.current.59016` link inside `releases/0.1.12`.

**Nothing failed.** Every upgrade after the first was a silent no-op that
reported success — the worst shape of this bug, and exactly the "boots but never
updates" case §11 escalates on. S11 never caught it because it only ever tested
a *fresh* install: host #1's first run is the only one that worked.

## The fix, and what proves it

The name is freed first and the new link renamed into it, so there is no
destination for `mv` to inspect. `previous` is kept so a failed rename puts the
old link back rather than leaving the host with no `current` at all, and the
result is read back with `readlink` — this failure's character is that it
reported success, so "installed" has to mean "`current` points at it".

Fixed in the capability (genproj #28) and, because `scripts/` is app-owned and
seeded once, in this repo's copy of the same file. The two bodies are byte-for-byte
identical.

The capability's tests now include two that **run the launcher for real** — a
real manifest and a real tarball over `file://`, from a host whose `current`
already points at an unpacked release — asserting what the host executes
afterwards and that no stray link is left behind. Restoring the old flip fails
all three of them. The static test they replaced asserted the buggy line, and no
static test could have caught this: the script with the defect passed every one.

The shipped copy was exercised the same way, on this box:

```
fetch-launch: installed 0.1.15 (any)
NEW
current -> /tmp/.../releases/0.1.15
strays: 0
```

## Item 5: PASS, on a real host (mac-studio, 0.1.14 → 0.1.15 → 0.1.16)

mac-studio was reinstalled, so its first run was a fresh install (0.1.14) — the
case that always worked. Release 0.1.15 and then 0.1.16 followed, which made the
*next* two runs genuine upgrades, host `current` already pointing at a release.
`memos/DJK2WkqZrDhFZ54JPfFh63`:

```
fetch-launch: installed 0.1.15 (aarch64-apple-darwin)
...
fetch-launch: installed 0.1.16 (aarch64-apple-darwin)

current -> /Users/nick/.local/share/a2a-goose/releases/0.1.16
releases: 0.1.12  0.1.14  0.1.15  0.1.16
strays: 0
```

Two upgrades in one sitting, `current` moved each time, no `.current.<pid>`
anywhere. The triple resolved to `aarch64-apple-darwin` (item 1), the new link
replaced the old rather than landing inside it, and the release the agent
actually runs is the one `current` names. Item 5 is proven.

**The supervisor is a git checkout.** The thing launchd runs on mac-studio is
*not* a release — it is the git checkout at `~/src/a2a-goose`, and on this host
it was **4 commits behind**, which is why the first reinstall still ran the buggy
flip: `git pull` was the actual fix, not the release. A host's launcher is
whatever that checkout happens to contain, so the code that supervises
everything else is un-pinned. (The launcher fix reaches a host this way, not
through the tarball — the release tarball is the agent binary, not the launcher.)
This is a real gap and needs a decision, not a quiet patch: **pin the launcher**
(the checkout is a deliberate, versioned install) **or fetch it** like everything
else. It is **decided at the end of this file** — fetch it, digest-pinned — and
the argument for it is there rather than here.

## Decision: the launcher is a release asset — fetch it, digest-pinned

The provenance gap above is decided here rather than left as a question: **the
launcher fetches the release including itself, and replaces itself in place
before it execs the payload.** Cold start is a `curl` from the README; every
start after that is self-updating.

Two options were on the table and neither survives alone:

- **Pin it** (the checkout is a deliberate, versioned install). Simple, no
  chicken-and-egg, the supervising code is human-reviewed before it runs — but
  drift is invisible, which is precisely how mac-studio ran the buggy flip for
  four commits. A pin only means something if something watches it.
- **Fetch it** (the launcher is an asset like the payload). A launcher fix
  reaches a host — but the fetcher cannot fetch itself, so a second frozen
  bootstrap appears, and a bad artifact can now brick the node.

**Fetch it, digest-pinned** keeps the reachability and pays the bootstrap cost
inside the one file that already exists: the frozen floor is the *minimum* the
launcher must always be able to do — read the manifest, verify a sha256, rename
over itself, exec, fail open. Everything above that floor changes with any
release, because the copy that runs it is the copy being replaced.

### The contract

**Manifest.** A top-level `launcher` object beside `assets`, in the same
one-asset-per-line shape the launcher already parses:

```json
{
  "name": "a2a-goose", "version": "0.1.17", "tag": "v0.1.17", "commit": "…",
  "assets": { "aarch64-apple-darwin": { "file": "…", "sha256": "…" } },
  "launcher": { "file": "fetch-launch.sh", "sha256": "…" }
}
```

A separate key, not an `assets` target: `assets` is keyed by *target* and
consumed by the target lookup, and the launcher is not a target — a candidate
list must never resolve to it. Same line shape, so one parser reads both. A
manifest with no `launcher` key (older release, or a project with no release
pipeline) is a **no-op**: the host keeps running the launcher it has.

**Cold start.** The one case with nothing to fall back to. The README's command
installs the same file the running launcher maintains, at the path the init
system supervises:

```bash
dir="$HOME/.local/share/a2a-goose"; mkdir -p "$dir"
curl -fsSL https://github.com/nickbrett1/a2a-goose/releases/latest/download/fetch-launch.sh \
  -o "$dir/fetch-launch.sh" && chmod +x "$dir/fetch-launch.sh"
```

The init unit points at `$dir/fetch-launch.sh`, not at a checkout.

**The swap.** Download beside the running file (same directory, so the swap is a
rename and not a cross-device rewrite), verify, `bash -n`, `cmp` to skip a no-op
update, then `mv -f` onto the path. Before the `exec`, so the new launcher takes
effect next start; a failure at any step logs and continues with the working
launcher.

### Why the two rules matter

- **Verify before swapping, and fail open.** A truncated download, a GitHub error
  page, or a bad checksum leaves the working launcher exactly where it is and the
  host still boots. The checksum comes from the same manifest as the asset, so it
  guards against *corruption*, not a hostile release — the same trust level the
  payload has today.
- **Rename over the path; never write through it.** bash reads a script lazily,
  off its inode, as it runs — rewriting the file in place would corrupt the
  process mid-execution. `mv` of a new file onto the name is the same lesson as
  the `current` flip in this spike, for the same reason.

### The new obligation

Pinning could not answer *"is this host's launcher current?"*; this can, and it
must. `/status` should report the launcher's version and digest beside
`acp.serve`, because "we shipped it" is only true if a host can be seen to have
it.

### What it changes here

The plist currently names a checkout and says the launcher "is a repository file,
not a release asset, so it is installed by hand and stays put". Mac-studio's
launcher is a **git checkout** (`~/src/a2a-goose`, 4 commits stale). After this:
the launcher is an asset, the unit points at a fixed path under `DEPLOY_DIR`, and
cold start is a `curl`.

**Implemented.** The generated half is in genproj — `github-release` publishes
the launcher and advertises it (`#29`), `fetch-launch` replaces itself (verify,
parse-check, rename over the path, fail open). This repo's seeded copies were
ported to match: `scripts/fetch-launch.sh` is the rendered capability file,
`scripts/release-artifacts.sh` now publishes the launcher and hashes it into the
manifest, `LAUNCHING.md` and `deploy/` document the cold start, and both units
name `$HOME/.local/share/a2a-goose/fetch-launch.sh` instead of the checkout. The
DSM wrapper stays a checkout file — it is the init glue, thirty lines that
rarely change — and mac-studio's plist needs the one-time cold start before its
next boot.

**The obligation is met.** The launcher exports `FETCH_LAUNCH_PATH`,
`FETCH_LAUNCH_VERSION` and `FETCH_LAUNCH_SHA256` on the way to its `exec` (after
the host's env file, so host-local configuration cannot overwrite the answer),
and `/status` reports them as a `launcher` object beside `acp` —
`{"managed": false}` when there is no launcher, which is what a test or a hand
start looks like. `version` is the release the launcher last verified itself
against, because a launcher has no version of its own; `sha256` is the file on
disk, taken *after* the self-update, so it names the launcher that will supervise
the next start. Equal to a manifest's `launcher.sha256` exactly when the host is
current, which is the question pinning could not answer.
