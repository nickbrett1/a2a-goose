# S6 — Does the deployed goose advertise `sessionCapabilities.close`?

**Plan (§4):** *Call `initialize` and read `agentCapabilities`.* **Gates §6.4's
session lifecycle**: if `close` is advertised, the agent can retire a session
explicitly (and goose can flush/persist); if not, the agent is limited to
`session/cancel` and must leave the session dangling in `sessions.db`.

## Method

`POST /acp → initialize` against the deployed goose and read
`result.agentCapabilities`.

## Evidence

Verbatim `result` (goose 1.50.0, `127.0.0.1:3284`):

```json
{"protocolVersion": 1,
 "agentCapabilities": {
   "loadSession": true,
   "promptCapabilities": {"image": true, "audio": false, "embeddedContext": true},
   "mcpCapabilities": {"http": true, "sse": false},
   "sessionCapabilities": {"list": {}, "delete": {}, "close": {}},
   "auth": {},
   "_meta": {"goose": {"recipeParameterScopes": {}, "localInference": {}}}},
 "authMethods": [{"id": "goose-provider", "name": "Configure Provider",
                  "description": "Run `goose configure` to set up your AI provider and API key"}],
 "agentInfo": {"name": "goose", "version": "1.50.0"}}
```

The same `initialize` was issued to the `--platform desktop
--enable-scheduler` instance on `:3285`; the result is byte-identical apart from
the runtime connection uuid (see [S1](S1.md)).

## Verdict

**PASS.** `sessionCapabilities` advertises all three of `list`, `delete` and
`close`. So:

- **`session/close` is available** on the deployed goose. The agent's session
  lifecycle is `new → prompt* → close` (with `session/cancel` as the interrupt
  path), not `new → prompt*` and leak. §6.4's "cancel-only" fallback is not
  needed.
- **`session/list` and `session/delete` are available too**, which the agent did
  not strictly need but is useful for reconciliation: the node agent can
  enumerate goose's sessions and drop any that no live `contextId` maps to, on
  its own startup, without touching `sessions.db` directly.
- **`loadSession: true`** — the agent can reattach to an existing session after
  its own restart. That is what makes §6.5's contextId→sessionId map recoverable:
  the map is still ours, but the sessions it points at can be reloaded rather
  than recreated.

## Consequences for the plan

- §6.4 — use `session/close` on A2A `tasks/cancel` and on agent shutdown.
- §6.5 — the contextId↔sessionId map can be rebuilt against live sessions via
  `session/list` + `loadSession`, so a lost map is a recovery problem, not a
  data-loss problem.
