# S7 — Does `protocolVersion: "1.0"` survive a caller with no `a2a-version` header?

**Status: PASS — and the premise dissolves.** Deferred until M1 because it needs
a2a-rs's server; M1 built one, so the header was measured against the real
router. The answer is not "it defaults to 1.0" and not "it rejects": the pinned
server **never reads the header at all**.

## The question

The plan's card advertises `protocolVersion: "1.0"` (§6.1). LiteLLM's A2A route
(`/a2a/{agent_id}`, see [S5](S5.md)'s synthesised card) speaks JSONRPC. The open
question: when a caller sends a request with **no** `a2a-version` header at all,
does the a2a-rs server

- accept it and default to 1.0 (compatible, nothing to do),
- reject it with a version error (we must document the required header, and
  LiteLLM may not send it),
- or silently negotiate something else?

## Why it gates M1

If a2a-rs requires the header and LiteLLM does not send one, then every call
through the LiteLLM A2A route fails with a version error that looks like a
protocol bug and is actually a header negotiation. That would be a bad first
impression of the whole system, and it is much cheaper to learn in a spike than
in a live call.

## Method

`a2acli` does not exist (see [S13](S13.md)), so: four `SendMessage` calls against
M1's server on `127.0.0.1:10099`, differing only in the `A2A-Version` header, plus
a card fetch with a deliberately wrong version. Then the SDK source, to see
whether this is policy or accident.

## Evidence

| `A2A-Version` sent | Result |
| ------------------ | ------ |
| *(absent)* | **200** — `TASK_STATE_COMPLETED` |
| `1.0` | **200** — `TASK_STATE_COMPLETED` |
| `0.2` | **200** — `TASK_STATE_COMPLETED` |
| `9.9` | **200** — `TASK_STATE_COMPLETED` |

Identical bodies in all four cases:

```json
{"jsonrpc":"2.0","id":1,"result":{"task":{"contextId":"01a0ab1b-b8b7-…","id":"01a0ab1b-b8b6-…","status":{"message":{"messageId":"01a0ab1b-b8b7-…","parts":[{"text":"stub: skill=ask dispatch=ask cwd=<goose default> message=hi"}],"role":"ROLE_AGENT"},"state":"TASK_STATE_COMPLETED","timestamp":"2026-09-16T16:43:33.…"}}}}
```

And the card, fetched with `A2A-Version: 0.2`, still advertises 1.0:

```json
{"name":"mac-studio-goose", … "supportedInterfaces":[{"url":"…:10099","protocolBinding":"JSONRPC","protocolVersion":"1.0"}], …}
```

The source explains it. `A2A-Version` exists as a **constant only**:

```
a2a-lf/src/lib.rs:23:  pub const SVC_PARAM_VERSION: &str = "A2A-Version";

$ grep -rn "A2A-Version\|SVC_PARAM_VERSION" a2a-server-lf-0.4.4/src
(no matches)
```

The server does not validate it, does not default it, does not negotiate it. It
merely hands *all* headers to the executor as a generic bag
(`jsonrpc.rs:57` calls `middleware::extract_service_params(&headers)`), so the
header is visible to our executor if we choose to look — but the router will
never refuse a call over it.

The client, meanwhile, **always sends it**:

```
a2a-client-lf/src/client.rs:24:  default_params.insert(SVC_PARAM_VERSION.to_string(), vec![VERSION.to_string()]);
```

That is why this was never noticed: the SDK's client and the SDK's server always
speak to each other through a header the server ignores. Nothing in CI would ever
have caught it.

## What this changes

1. **The risk is void, in both directions.** LiteLLM not sending the header
   cannot break anything, so the "bad first impression" this spike was gating on
   cannot happen. The carve-out in §6.1 does not need writing.
2. **But "a wrong version fails cleanly" is *not* true today**, and the plan
   implies it is. `A2A-Version: 9.9` is accepted and answered in 1.0. If we want
   a version refusal, **we** have to write it — a tower layer next to the bearer
   check, or a check in the executor reading `ExecutorContext::service_params`.
   The SDK will not do it for us.
3. **Recommendation: do not add it in M1.** Our config already refuses to *start*
   on a protocol version we do not know (`ACCEPTED_PROTOCOL_VERSIONS`), which is
   a host-operator guard where a mistake is cheap and loud. A per-request version
   gate would instead invent a refusal the SDK does not make, on a header the
   ecosystem's own client sets and no server reads — asymmetry for its own sake.
   Revisit only if a real caller sends 0.3 and mis-reads a 1.0 reply.
4. Note for the ACP leg: `service_params` is where headers land, with lowercased
   names, so `x-litellm-trace-id` is readable there — that is the hook §6.7's
   trace-id forwarding would use, bounded by [S2](S2.md)'s decision.

## Verdict

**PASS** — the question's premise does not hold. `protocolVersion: "1.0"` is not
negotiated, it is simply declared and never checked; a caller with no
`a2a-version` header is indistinguishable from one with `1.0`. Nothing to do for
M1; the finding to carry forward is the *negative* one, that if we ever want a
version refusal, it is ours to write.
