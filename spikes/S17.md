# S17 — Why did the Mac's agent keep losing its ACP port?

**Status: PASS — the thief was the editor, not the agent, and the fix is one
setting.** On 2026-09-17 `mac-studio`'s agent refused to start with
`http://127.0.0.1:3286 is already in use: something is listening there but did
not answer an ACP \`initialize\`` while `ps` showed no goose and no second agent.
`lsof` named the holder: **`Code\x20H` (VS Code's own helper process) LISTENing
on `*:3286`** — a *forwarded port*, the client-side end of a dev-container
forward, which binds every interface on the host whether or not the container
end is alive. The port had been taken out of the agent's hands by the editor
that was merely *observing* the agent, and the observation channel was
**terminal output**.

Agent back up the same day on `127.0.0.1:32841`, registered, and answering
through LiteLLM's `/a2a/{agent_id}` route.

## The question

Does a host-level agent on a machine that also runs a VS Code dev-container
session own its loopback port? The plan says `goose.acp.serve: own`
(hard constraint #14, [S14](S14.md)) — the agent starts and supervises the goose
on a loopback address. What it does not say is what happens when something else
on that machine decides the same port is interesting.

## What it was not

- **Not an orphan goose.** Every earlier failure of this shape *was* one (a
  `SIGKILL`ed payload leaves a `goose serve` behind, and the next payload refuses
  to adopt it — [S8](S8.md) §5). Here `ps -o pid,ppid,args -w -ax | grep goose`
  found nothing, and `pkill -f 'goose serve … --port 3286'` matched nothing: the
  port was held by a process that never had an ACP server behind it.
- **Not a second agent.** No `a2a-goose` process existed; `launchctl print`
  showed the job in `spawn scheduled` with `last exit code = 1`, i.e. the agent
  was in its keep-alive retry loop, losing the same race every 30 s.
- **Not the port being "in use" in the ordinary sense.** Nothing was serving
  HTTP on 3286: a connection was accepted and then hung, which is what a
  forwarder with a dead target looks like.

`lsof -nP -iTCP:3286` on the Mac:

```
COMMAND    PID USER  ...  NAME
Code\x20H  983 nick  ...  TCP *:3286 (LISTEN)
```

and the same process held `*:3284`, `*:3285`, `*:3299`, `*:3399`, `*:10001` —
every port the project's own spikes and config examples had ever printed.

## The mechanism, measured

`remote.autoForwardPortsSource` was `"hybrid"` on this machine, which means VS
Code forwards ports from **process detection *and* from terminal output**. The
output half is a scraper: any `host:port` that appears in a terminal becomes a
forwarded port, and a forwarded port is a client-side listener bound on
`remote.localPortHost` (measured: `allInterfaces`, i.e. `*:port`).

Probes, same terminal, 25 s apart in effect:

| Line printed in the terminal | Forwarded? |
| --- | --- |
| `probe (hybrid, before fix): http://127.0.0.1:32901/acp` | **yes** — `Code\x20H 983 … TCP *:32901 (LISTEN)` within 25 s, with nothing listening inside the container |
| `probe (after fix, source=process): http://127.0.0.1:32902/acp` | **no** — no listener on the host, 30 s later |
| `bind(("127.0.0.1", 45100))` held by python for 45 s on the **host** | **no** — a host listener is not a container process, so even the process half does not see it |

So the trigger is not "something is listening" and not "something on the host is
listening". It is *the URL having been printed*. The agent's own config is the
poorest possible place for a secret like a port: the moment
`url: "http://127.0.0.1:32840/acp"` was echoed while reading the file back, the
editor took `32840` too — 5 s later the agent's next attempt reported
`32840 is already in use`. The moving-target behaviour in that config's comments
(3284 → 3285 → 3286, each "outside every forward VS Code holds") was this
scraper following the agent around.

The container-side log agrees about what the forward *is*
(`~/.vscode-server/data/logs/<session>/remoteagent.log`):

```
[error] [remote-connection] Failed to connect tunnel to localhost:3286:
        A system error occurred (connect ECONNREFUSED 127.0.0.1:3286)
```

— a client listener on the Mac, retrying every ~30 s against a container port
where nothing listens, forever, or until a human stops forwarding it.

## The second symptom, found by a second host

`*:10001` was in that list too — the agent's A2A port, forwarded because the
address had been printed. The consequence: the Mac's **LAN address was a dead
end**. Measured by the NAS agent, from the NAS and from inside the LiteLLM
container:

| Dialled | Result |
| --- | --- |
| `http://100.77.144.14:10001` (tailnet) | **reachable** — HTTP `401`, i.e. up and merely unauthenticated |
| `http://192.168.1.33:10001` (LAN) | TCP connects, **no HTTP response ever** — the editor's listener, tunnelling to nothing |

Which is the answer to a question that looked like a networking problem: the
card must carry the tailnet address (`A2A_GOOSE_BIND`/`PUBLIC_URL` already did),
and the LAN alternative is not "blocked by a firewall", it is **occupied by the
editor**. It also corrects S9's blanket "the LiteLLM container cannot reach the
tailnet at all": on this day the container reached mac-studio's tailnet IP
directly, so the tailnet path to a peer works and the literal is the right
`url`.

## The fix

1. `"remote.autoForwardPortsSource": "process"` — the output scraper off, the
   container-process detection kept. Verified by the second probe above.
2. Move the agent to a port the scraper has never seen and set it in the config
   with the reason: **`127.0.0.1:32841`**. It is also outside macOS's ephemeral
   range (49152–65535), so nothing else allocates it by accident.
3. The entries already in the Ports panel are **not** removed by the setting
   change. Each one stays a listener on all interfaces until a human stops
   forwarding it (`remote.localPortHost` is `allInterfaces` here, so they are
   not even loopback-only). That is housekeeping owed on this box, not a code
   change.

Rule that falls out of it: **a host-level process must not choose a port whose
literal has been printed in an editor terminal.** That includes the port being
printed by the agent's own config, this spike, and the transcript of this
session. If it matters, do not echo it — and if the machine is a dev box, turn
the scrape off first.

## Restarting the macOS host's agent

Different signal surface from DSM, same rule about `SIGKILL`:

| State | Command | Note |
| --- | --- | --- |
| payload running | `kill -TERM <payload pid>` | graceful: it stops the goose it started and deregisters; launchd's `KeepAlive` relaunches |
| job down (`state = spawn scheduled`, `last exit code = 1`) | `launchctl kickstart gui/<uid>/com.nick.a2a-goose` | plain `kickstart` starts a job that is not running — nothing to kill |
| payload running, and you are tempted by `kickstart -k` | **do not** | `-k` is a `SIGKILL`: it orphans the `goose serve` child, and the next payload refuses to adopt it (S14) |

Measured on the Mac: `SIGTERM` at `21:10:19Z` → `serve: ready`, `registry:
registered` at `21:10:27Z` — **8 seconds**, with no sessions in flight. The 69 s
shutdown in [RUNBOOK.md](../RUNBOOK.md) is the NAS case and included a live
session; budget two minutes either way.

## Turn latency — CORRECTED, see [S18](S18.md)

While proving the chain after the fix, one turn took **~8 minutes** and the next
turn on that context took **2 s**, and this file originally recorded that as
"the first turn on a new `contextId` is the expensive one — session and
extension startup". **That attribution is wrong.** Re-measured deliberately one
day later on this host (S18): a brand-new `contextId` on a warm payload is
**1.9 s**, the first turn after a `SIGTERM` restart is **2.4 s**, three
simultaneous turns on three new contexts on a just-restarted payload are
**2.4–2.8 s each**, and a substantive tool-using turn is **3.9 s**. There is no
warm-up cost to budget for; size a caller's timeout to the task, not to startup.
The durable advice that survives is narrower: reuse a `contextId` for
continuity, and have a long-running agent write its result down before
explaining, so a caller that gives up early loses the reply and not the work.

Also from S18: **`agent_id` changes on every payload restart** (three different
ids across three restarts here), so resolve by name rather than holding an id.

## Verdict

**PASS.** The port was never the agent's to lose by itself: a host that also
runs an editor with output-based port forwarding has a second writer for any
loopback port whose literal it has seen. Fixed at the source (one setting), the
agent moved to `32841`, both hosts are on the roster, and a real turn comes back
through LiteLLM. The remaining work is housekeeping on the Ports panel and the
timeout question above — not this one.
