# Releasing a2a-goose

A release is cut by CI. There is no version file to bump, no tag to push by
hand, and no release to draft: the version is derived from the last tag, the
tag is created by the release step, and the release is published with notes and
whatever artifacts the project packages.

## Cutting a release

1. Merge to the default branch. Buildkite builds and tests the commit.
2. The release step runs automatically, exactly like the deploy step: it bumps
   the version from the newest existing tag, creates the tag `v<version>`,
   attaches the build's artifacts, and publishes the GitHub Release.

The `v` prefix is a fixed convention, not a setting: it is what the step scans
for and what it creates. An existing repository adopting this pipeline should
re-tag its releases to `v<major>.<minor>.<patch>` so version bumps continue the
real series instead of restarting at `v0.1.0`.

Watch it under the repository's **Buildkite** build, not its Actions tab —
there is no GitHub Actions workflow here.

## What is in the release

| Piece | Comes from |
| ----- | ---------- |
| Tag `v<version>` | Created by the release step. The first release is `v0.1.0`; after that it is a patch bump of the newest tag |
| Release notes | Generated by GitHub from the pull requests in the release, classified by `.github/release.yml` (`--generate-notes`). |
| Assets | Uploaded by the build step as Buildkite artifacts, downloaded by the release step, and named by `scripts/release-artifacts.sh` |

The release is created only after build and test passed **on that commit**, in
that same build, because the release step depends on the build step. A release
cannot exist for code that did not pass.

## How the artifacts get from the build to the release

Each Buildkite step runs in its own container, so the release step never sees
the build step's working tree. It does not rebuild it either: the build step
uploads its output (`artifact_paths:` in `.buildkite/pipeline.yml`) and the
release step fetches those exact bytes back from the Buildkite artifacts API:
it lists this build's artifacts, keeps the ones under the build step's own path
prefix, and downloads each with `curl`. One compile per commit, and the release
attaches what the tests actually ran against.

The fetch deliberately does not use `buildkite-agent artifact download`. That
call reaches the agent binary mounted from the host, and this fleet runs macOS,
so the mounted binary is unlaunchable inside the step's Linux container. The API
needs no agent binary — only this job's own access token, which the docker plugin
forwards into the container.

## Changing what is shipped

Two places, depending on what you are changing.

**Which files are carried between the steps** lives in `.buildkite/pipeline.yml`:
the `artifact_paths:` list on the build step and the matching fetch in the
release step. That file is genproj's and is rewritten
on every regeneration, so treat it as generated — change the project's saved
configuration instead, or expect to re-apply the edit. `artifact_paths:`
does not fail when a pattern matches nothing, so a build that outputs somewhere
else releases notes only until the patterns are corrected.

**What is attached to the release** is `scripts/release-artifacts.sh`, which is
yours. It is seeded by genproj once and is never overwritten on regeneration (it
lives under `scripts/`, which is app-owned). Edit it to change the artifact
names, ship one file per platform, sign or notarise, or add a launcher manifest.
It packages `dist/` by default, and produces no assets if there is nothing
there.

Asset **names** are a contract: anything fetching
`releases/latest/download/<name>` depends on the exact string, so treat a name
as frozen once something consumes it.

## The release manifest

Every release carries `manifest.json` at a **fixed** name, so it is fetchable
without knowing the version:

```
https://github.com/<owner>/<repo>/releases/latest/download/manifest.json
```

It lists one entry per attached artifact, keyed by **target**:

| Key | Meaning |
| --- | --- |
| a Rust triple (`aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`) | A binary for that architecture and C library |
| `any` | An architecture-independent payload (a JS bundle, a pure-python `.pyz`) |

Each entry carries the asset `file` name and its `sha256`. A launcher reads the
manifest, picks the first key matching its host, downloads `file` and verifies
the hash — it never constructs an asset name. Labels are the Rust triples only:
the triple is what `cargo --target` takes, and every Linux target here is musl,
so one binary runs on a musl host and a glibc host alike.

**An asset name must not embed a version.** Version and hash live in the
manifest; the name carries the target only. `manifest.json` is written last so
it never advertises a file that is not there.

## Primary language

The project builds, tests and releases **one** language — its Primary Language
(`language` in the project configuration). `devcontainer-*` capabilities are
toolboxes, not CI targets: a rust devcontainer alongside a python primary is a
dev toolchain, not a second release. When two or more devcontainers are
selected the language must be declared, because selection order must not decide
what ships.

## Prerequisites

- A release-write token, resolved at run time and never stored in the
  repository: with the `doppler` capability selected, the release step reads
  `GITHUB_RELEASE_TOKEN` from the `common` Doppler project (`prd` config); the
  agent forwards only `DOPPLER_TOKEN` into the container.
- Without `doppler`, the step expects `GH_TOKEN` in the agent's environment —
  the same fleet-side contract the deploy step uses for `CLOUDFLARE_*`.

## What this does not do

- **It is not a validator.** Buildkite is the only validator; the release step
  reads that verdict rather than producing one of its own.
- **It does not choose the version.** Versions are patch bumps from the last
  tag, so there are no major/minor releases. Tag a version by hand once, and CI
  will continue from there.
